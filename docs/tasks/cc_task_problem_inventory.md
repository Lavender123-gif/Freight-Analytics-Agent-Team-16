# 任务：运费争议文本处理的问题清单与流程拆分

## 你的角色

你是这个项目的分析员，不是开发者。这个任务**不写流程代码**，只做数据分析和设计论证。分析脚本可以写，放在 `scratch/analysis/` 下。

报告用中文写，不使用破折号（—）。字段名、代码名保留英文。

## 项目背景

- 客户：PPG Industries（大型制造商），联系人 Jake。项目信息默认保密。
- 数据：从 Oracle Transportation Management（OTM）手动导出的 AutoPay 争议记录。每行是承运商对一张运费发票的一次调整申请：系统预计金额（`Shipment Amount`）、承运商开票金额（`Invoice Amount`）、两者之差（`Delta`），以及承运商写的自由文本说明（`Descritipion`，原列名拼写如此）。
- 现状：PPG 约 70 人的审核团队人工阅读这些文本决定是否付款，没有 SOP，常常"差不多就放过"。
- 项目范围：把自由文本转成标准化的、逐项列出的 line items，加上简单的逻辑检查和风险提示。**判断该不该付款不在范围内。**
- 产品方向：即使本项目不做，也要为承运商管理打好数据基础（承运商评估、争议率、文本清晰度、返工和人工介入次数、错误模式，用于承运商培训）。
- 课程要求（CMU Intro to AI）：agentic workflow、预训练模型、至少 5 个自定义工具、skill 文件夹、评估方法、数据保护、安全护栏的有无对比。

## 硬性约束

1. **只用开发集。** 仓库里已经按 shipment 做过开发集和测试集切分。先找到切分文件，只读开发集。**不要打开测试集，也不要读原始的完整 Excel。** 如果找不到切分文件或不确定哪个是开发集，停下来问。
2. **不从脚本调用任何 LLM API。** 账号规则是只用订阅、不用 API 额度。需要"LLM 判断"的地方，由你在会话里亲自阅读样本来判断，并说明样本量。
3. **报告里不出现人名。** 数据文本里有 PPG 员工和其他人的姓名，引用例子时替换成 `[PERSON]`。
4. **数字必须来自脚本。** 报告里的每个计数、比例都要能由 `scratch/analysis/` 下的脚本复现。区分"已验证的事实"和"推测"，推测要明确标出。
5. **不写承运商专属规则。** 方案要能推广到没见过的承运商。

## 设计原则（评判任何方案的标准）

1. **Baseline 是"每条记录直接交给 LLM"**，配一段认真写的 prompt，不加任何工程。数据量下成本不是约束。所以任何一个组件都必须说清楚：它在准确性、稳定性、安全性或可审计性上比 baseline 好在哪里。说不清的组件不要。
2. **不允许静默错误。** 每一种错误，要么在运行时被发现，要么它的发生率能在离线评估里测出来。不完美的组件可以接受，前提是它的失败能被明确识别出来并交出去处理。
3. **LLM 只负责理解。** 计算、校验、调度、flag 生成都由代码完成。
4. **能用代码确定判断的，不交给 LLM；需要理解语义的，不用关键词规则硬做。**

## 已验证的事实（在全量数据上测得，请在开发集上复核，不必花时间重新发现，但要看得比这些更远）

- `Delta` 在全部行上精确等于 `Invoice Amount − Shipment Amount`，按系统计算处理。
- `US/CAN` 列全部填 US，但大部分行的目的地是加拿大省份，此列不可信。
- `PK` 实际是发票号，不唯一，约三分之一为空。同一个 PK 下可以有多次争议（不同时间、不同文本、不同 Delta）。
- `Delta` 有等于 0 和小于 0 的行，内容混杂（费率主张、追讨付款、结案记录、空白、承运商少收）。
- `Reason Code` 绝大多数是"其他附加费"，有专门代码的类别（如危险品、等候费）也很少被使用。
- 文本里约 61% 的数字前面有 `$`；存在空格千分位（如 `1 684.68`）、以点开头的小数（`.68`）、时间戳。
- 存在一个金额对应多项费用的写法（如 `TAILGATE AND PURCHASE FEE BALANCE DUE $35`）。
- 存在一段文本同时讲付款历史和多项费用的写法（已开票、已付、扣减、未付混在一起）。
- `PURCHASED TRANSPORTATION SURCHARGE / FEE` 一类写法占数据大头，含义尚未确认。

## 第一阶段：问题清单

**这一阶段不要阅读 `docs/design/` 下的任何文件**，避免被现有设计带偏。

### 要回答的问题

从 baseline 出发：把一条记录加一段 prompt 交给 LLM，要得到可信、标准化、可审计的 line items，整个流程到底要解决哪些问题？

以下是起点，不是完整清单，请补充、合并或否定：

- 数据标准化：数字、金额、单位、日期、费用名称的写法统一
- 争议分类：是否需要给每条争议分类？如果需要，**分类的用途是什么**（给审核员看、给下游代码用、还是帮 LLM 判断更准）？不同用途对分类的要求不同。说不出用途的分类不要做。
- 简单检查：税率是否正确、金额加总是否等于 Delta、文本内部算术是否自洽
- 信息缺失：做出关键判断需要的信息，记录里是否缺失（比如只写了 `+ HST` 没写金额、只写了金额没写费用名称、完全没有说明）
- 其他你在数据里发现的问题

### 每个问题要写清楚

| 项目 | 要求 |
|---|---|
| 定义 | 一句话说清楚问题是什么 |
| 数据证据 | 开发集里的发生次数，2 到 3 个去除人名的例子 |
| baseline 会怎样 | LLM 直接处理会不会出错；出错时是**静默**的还是看得出来的 |
| 所需信息 | 解决它需要哪些信息 |
| 信息在哪里 | 分为四档：①记录本身（文本或结构化字段）就够；②需要我们能自己建立的参考资料（费用代码表、税率表等）；③需要客户提供的数据（合同费率、PPG 内部清单、运单总量等）；④目前无法获得 |
| 谁来解决 | 确定性代码、LLM、人工，或解决不了 |
| 如何发现失败 | 运行时怎么发现，或者离线怎么测 |

### 输出

`docs/analysis/01_problem_inventory.md`，结构为：

1. 问题清单（按上表逐项）
2. 按"信息在哪里"四档汇总：哪些问题凭现有信息就能处理，哪些需要建参考资料，哪些需要向 Jake 要数据，哪些做不了
3. 要问 Jake 的问题清单
4. 你认为最影响整体成败的三个问题，以及理由

**完成第一阶段后停下来，在会话里用几段话汇报结论，等待确认再进入第二阶段。**

## 第二阶段：数据结构与流程拆分

**这一阶段仍然不要阅读 `docs/design/`。**

### 要回答的问题

基于第一阶段的问题清单，看数据结构，回答怎么拆分处理流程比较合适。

1. **数据单位**：发票、一次争议、一个 line item 之间是什么关系？每一层需要什么唯一标识？同一张发票的多行，哪些是独立争议，哪些是同一争议的重复提交，能否区分？
2. **数字的维度**：文本里的一个数字需要用几个独立维度来描述，才能既不丢信息、又能支撑对账？（比如"它是什么"和"它处于什么状态"是否应该分开？一个金额能否对应多个费用代码？）
3. **流程拆分**：提出至少两种不同的拆分方案。每种方案说明：
   - 分几个阶段，每个阶段的输入和输出（给出 JSON 结构草案）
   - 每个阶段解决第一阶段的哪些问题，哪些问题留到了哪里，哪些没人解决
   - 哪些阶段是代码、哪些是 LLM、哪些需要循环（模型做一次、收到反馈、再做一次）
   - 相对 baseline 的增益在哪里，代价在哪里
4. **推荐**：选一种方案，说明理由；说明在什么实验结果下你会改选另一种。

### 输出

`docs/analysis/02_decomposition.md`

**完成后停下来汇报，等待确认再进入第三阶段。**
