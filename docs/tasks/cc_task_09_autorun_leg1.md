## 0. 这次和以往不同的地方

以往是一份任务书做一件事，做完我逐条看。这次我时间很少，把一整段工作交给你自主推进，我只在两个点上看：

- **停点一（今晚，我在场）**：第一批真实模型调用跑完。
- **停点二（第一个验收节点）**：主线用真实模型全线跑通，验收包备好。

两个停点之间不要停下来问我。授权原则只有一条：

> 不是大方向、不会让项目跑偏的决定，你自己定，定完记入决定日志。可能改变大方向的，不要自己定，也不要停工：选最保守的做法，做成配置项，记入待决清单，继续往下做。

允许你为了把事情做对多花 token：开子代理、做交叉验证、重复运行都可以。

## 1. 大方向（冻结，不许改）

仓库里的 `CLAUDE.md` 和最新的设计、schema、计划文档是权威。下面是摘要。如果摘要和仓库文档冲突，以仓库为准，并把冲突记入待决清单。

1. 范围：把承运商文本拆成标准化 line items，加逻辑检查和标识。不判断该不该付款，输出里不出现"有效""应付"这类结论。
2. 不写任何针对特定承运商的规则、措辞或例子。
3. 每条记录都经过模型，模型之前没有自动打回的分支。系统不自动采取任何行动，每条记录最后都到审核员手里。
4. 盲解析：模型看不到 Delta，输入和 SKILL.md 里都不出现。对不上时只告诉模型"不一致"（不说是谁的错，Delta 也可能错），允许它重试并说明理由。第一次尝试必须留存。不一致交给审核员判断，系统不替他裁决。
5. 三种建议：建议退回承运商、建议人工审核、解析通过检查。颜色由规则计算，不由模型的自信程度决定。所有阈值在 `rules.yaml`。涉及税的一律到人工。
6. 不允许静默错误。任何不完美的部件，失败时必须显式标出来。
7. 重复：只标识，不判断是否正常。多层级（行内、发票内等）各自检查。每份副本是独立记录：第一次出现不标，之后每次出现都标，只能凭规则里写明的明确证据清除。
8. 不修改源 Excel。派生字段另存。输出分事实层和判断层。
9. 只做基于 Excel 的输入，不做任何 OTM API 相关设计。
10. 发给模型的文本必须先经过现有的脱敏步骤。

## 2. 禁区

- 不读、不碰测试集（切分出来的那 30%）和原始 Excel。
- 不读、不解压预留 mock，不进入 mock 生成项目的文件夹去找它。公开 mock 可以用。
- 不修改 mock 的期望答案。mock 归另一个代理维护。
- 不向任何远端推送（`git push` 一律不做）。
- 不在项目文件夹以外写任何文件，不用 `/tmp`。
- 不用 sudo，不改系统设置。
- 行级数据（含记录原文的输出）只写到 git 忽略的目录。提交进仓库的报告沿用现有脱敏约定：不出现 shipment 号、发票号、承运商代码、人名。
- 不把 API key 写进任何会被提交的文件，不在输出里打印它。

## 3. 工作范围和顺序

任务编号和完成标准以 `docs/plan/2026-11-05_workload_v2.zh.md` 第 3 节为准。这一段只做下面这些，顺序已调整为先打通模型。

### 阶段 0：对账（我在场）

1. 读 `CLAUDE.md`、状态板、上面那份计划、最近的任务书和报告。跑现有测试。
2. 用一屏告诉我：11 月 5 日之后仓库实际做到哪了，哪些任务已完成、哪些部分完成。以仓库现状为准，不以计划为准。
3. 新建分支 `autorun-leg1`，之后所有提交都在这个分支上。工作区有未提交的改动时，先告诉我，不要自行丢弃。
4. 在项目的 Claude Code 设置里为第 2 节的禁区加上 deny 规则（测试集路径、预留 mock 路径、`git push`、sudo）。这一步会触发确认，我在场会点。写完把规则给我看一眼。
5. 用 `.env` 里的 `ANTHROPIC_API_KEY` 做一次最小的真实调用，确认能通。模型用 Sonnet 5.5（模型 ID 请对照官方文档核实，我记的是 `claude-sonnet-5-5`）。
6. 建好预算账本（见第 5 节）。

阶段 0 做完不用等我，直接进阶段 1。

### 阶段 1：B 链，到第一批真实调用

- P2 去掉旧路径
- P3 盲解析
- P4a 提交检查
- L2 工具说明和 SKILL.md 例子
- L1 接模型：先做到能在开发集上跑通 agent 循环，每次尝试留存，记用量

然后从开发集按承运商和写法分层抽 20 到 30 条，跑一遍。

**停点一。** 停下来给我一屏汇总：

- 首次不一致的有几条，模型被告知"不一致"之后各自怎么反应（原样坚持、改了并给理由、去掉某个金额来凑）。
- 平均几轮调用，实测每条成本，按第 6 节的运行量外推这一段和整个项目的花费。

等我回复"放行"再继续。我可能会在这里纠正方向。

### 阶段 2：A 和 D·E

- S1 schema 定稿为 v1：未决项按最保守的做法暂定，逐项记入待决清单
- S2 数据库和 Excel 接入
- P5 输出分事实层和判断层
- R1a 标识规则和颜色
- R1b 行内和发票内的重复

内部关口（不用找我）：

- 全部单元测试通过。
- 88 个边界用例过一遍。因为框架改了（不再有自动打回等），部分用例的期望值会过时。逐条标"保留、修改、作废"并写理由，理由必须对应到第 1 节的某条决定或某个已确认的 bug。
- 公开 mock 在确定性层（去重、脱敏、数字识别、检查、重复标识）上跑一遍。结果与 mock 期望不符时分三类：我们的 bug（修）、mock 期望因框架变化而过时（不改 mock，列清单）、说不清（列清单）。

### 阶段 3：规模运行

1. 从开发集再分层抽两份互不重叠的样本，A 和 B，各约 100 条。
2. 在 A、B 和公开 mock 上各跑一遍完整流程，记录基线数字。
3. 取 50 条各重复跑 3 次，报告同一条记录三次结果的一致率。
4. 失败归类：接线 bug、SKILL.md 或工具说明的措辞问题、框架层面的问题。
5. 措辞调优：只看 A 上的失败来改，改完在 B 和公开 mock 上验证。最多三轮。每轮记录改了什么、A/B/mock 上前后的数字。某一轮在 B 或 mock 上变差，就回退这一轮。
6. 框架层面的问题不要修，写进待决清单，附上例子和你的建议。

### 阶段 4：独立审计

开一个没有参与开发的子代理（全新上下文），只给它仓库和下面的清单，让它找问题，不是让它确认没问题：

- 从实际留存的请求内容里核对：Delta 有没有以任何形式进入模型的输入。
- 开发集样本里是不是每一条都到了模型，有没有被提前分流的。
- 有没有哪条路径失败了却没有任何标识（静默失败）。
- 首次尝试是不是都留存了，重试后有没有覆盖掉。
- 测试期望值、`rules.yaml` 阈值在这个分支上的全部改动，逐条核对理由是否成立。
- 有没有任何针对特定承运商或特定记录的硬编码。
- 禁区有没有被碰过。

审计发现的问题：属于 bug 的修掉并补测试；其余记入待决清单。审计报告原文保留。

### 阶段 5：验收包，然后停

**停点二。** 准备好下面这些再停：

1. **一屏汇总**：三种建议的分布、首次和重试后的不一致率、重复运行的一致率、失败归类、花费。数字分 A、B、公开 mock 三列。
2. **只读结果页**：一个本地静态 HTML（不引用任何外部网络资源），按发票展开到每条主张，显示颜色、标识、模型的说明、首次是否不一致。没有按钮，不记录任何决定。它含行级数据，放在 git 忽略的目录。
3. **抽查清单**：15 到 20 条，按规则抽（每种建议、每种主要标识各随机取，不是你挑表现好的），写明抽样规则，给出在结果页里的定位方式。
4. **待决清单**：每项写问题、选项、你暂定了哪个、之后改掉的代价。
5. **决定日志**：你自己定的每件事，一句话说定了什么、为什么。
6. **期望值和阈值改动记录**。
7. **状态板更新**（中英两版），按现有的证据分级规则，不许凭感觉升色。
8. **标注指南草稿（H1）**：给人工标注用，覆盖数字的含义、是否被主张、费用代码。只做草稿，不做标注本身。

最后在对话里给我一条不超过 30 行的消息：做到了哪、没做到哪、验收包的入口文件路径、我需要回答的问题有几个。

## 5. 预算

- 这一段模型调用的总上限是 **50 美元**，跨会话累计。
- 建一个账本文件，每次运行后把实际用量和折算金额记进去，每次运行前先读它。
