## 2. MVP 收敛（第一优先，必须做）

1. **票货汇总接进主流程**：`run_batch` 在合并副本之后调用汇总和"内部代码到客户名"的对照；结果写进库和导出。**评估和生产走同一条路径**：评估脚本改为调用主流程里的同一个函数，删掉评估专用的汇总调用。在任务 19 的存档读法上重放：主流程产出的票货结果必须和评估脚本原来算的完全一致，只有第 1 节第 1、2 条带来的变化例外，这些逐条列出。
2. **Jake 格式的票货表导出**（CSV 和 JSON）：每票货一组，包括原始运费；各项明细（客户名、内部代码、金额、状态、被谁取代），税单列；默认新总额；相对原始运费的变化；另一读法的总额；文字写明的应付数；gap；提醒；建议。用 Jake 两个例子的合成版做回归测试，必须精确复现。
3. **第 1 节第 1、2 条的实现和测试**。在开发集存档读法上报告：BALANCE DUE 规则改动让多少条说明的建议变了；gap 不为空的说明数、票货数和分布。
4. **输出接口**：写 `docs/shipment_output_contract.md`（英文），格式和 `reading_output_contract.md` 一样：票货层每个字段的含义、取值、合成例子、下游可能的用法。读法输出和票货输出都加 `schema_version`。
5. **扩展口**：每个口都要有接口、默认实现、测试和一段说明，不能只写在文档里。
   - **跨批次历史**：汇总接受一个 `prior_history` 输入；默认实现返回"未提供历史"。用三态区分：有历史、查过没有、未提供。输出里如实显示"未提供"，不能当成"没有重复"。
   - **读历史的 skill（候选）**：汇总里留一个"关系建议"的输入位，默认为空；规则 7（关系定不了）的票货在输出里有标记，方便以后接入。
   - **审核员反馈**：`reviewer_decision` 表能导出成 CSV，字段写进接口说明。
   - **代码表、规则、专题参考文件**：在 README 里写清楚，新增一个费用代码、一条规则、一个专题参考文件，分别要改哪个文件、要跑哪个测试。
6. **运行记录完整**：每次运行都记下代码版本（git 提交号）、脱敏方式、skill 布局、skill 和规则的版本、模型名。缺的补上。
7. **状态板对照现实**：逐张卡核对"声称做到了什么"和实际代码是否一致（例如票货汇总那张卡此前在主流程里并没有接上）。不一致的，改卡片的说法或颜色，并列出改了哪些。
8. **干净检出的冒烟测试**：从一个干净的检出（不含 git 忽略的文件）开始，只按 README 的步骤，用仓库里的合成样例跑通整条主流程（需要模型的部分用存档或桩），产出读法层输出、票货层输出和票货表。照着做不通的地方，改 README 或代码。
9. 全部测试通过；扫描被跟踪的文件，没有真实数据，也没有密钥（`.env` 不在跟踪里）。
