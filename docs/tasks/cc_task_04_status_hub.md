## 1. 背景与目标

这些文件以后会放到 GitHub 上给组员看。目标场景：组员问"你说完成了多少，依据是什么"，在 GitHub 上点开看板，看到整体进度；点某张卡片，看到这张卡的一屏摘要；再点一下，看到它的交付物和测试报告。组员看完觉得测试不够，可以据此校准进度。

所以每次卡片变色，都必须有对应级别的测试报告作依据。

GitHub 上 `.md` 文件会渲染，相对链接和页内锚点可以点；`.html` 文件只显示源码，不渲染。因此本任务的主入口是 Markdown 看板。

## 2. 新的颜色和证据级别

写进看板文件开头，替换原有颜色标准：

| 颜色 | 含义 |
|---|---|
| 红 | 没开始 |
| 黄 | 做了一部分，有明确缺口或待定项 |
| 浅绿 | 初步成型：已实现，开发集全量跑过，有交付物，但证据是样本内的 |
| 深绿 | 验证通过：在独立样本或人工审核上，达到事先写定的门槛 |
| 灰 | 仓库里没有依据，由我本人维护 |

证据级别，每份测试报告开头必须标明：

- **样本内**：用开发这部分时看过的同一批数据检验。
- **独立样本**：用开发时没看过的数据检验，例如合成注入的测试数据。
- **人工审核**：由写代码以外的人抽样核对，或在测试集终测中检验。

规则：

1. 浅绿要求至少样本内证据和交付物；深绿要求独立样本或人工审核证据，并且达到门槛。
2. 门槛必须在跑检验之前写进卡片的"完成标准"。现有检验如果当时没有事先定门槛，测试报告里如实写"门槛未事先设定"，这样的结果不能用来标深绿。
3. 分析类卡片（例如 A2 问题盘点、A3 设计方案）的"检验"是脚本可复现与数字核对，按实际情况标级别，在卡片里写明它是分析类。
4. 每张非深绿的卡片注明：升到下一档是否依赖接上模型（B04）。

现有 8 张绿卡默认归为浅绿，除非现有证据已经满足深绿的全部条件；逐张写明判断依据。

## 4. 看板的结构（生成结果）

中英两版结构相同，从上到下：

1. **整体进度**：两个数。成型度 = 浅绿与深绿卡片的加权占比；验证度 = 只算深绿的加权占比。权重和黄卡是否算部分分，由你提出方案，标 `[建议，待确认]`，写清楚计算公式。旁边写一句话说明两个数的区别。
2. **总览图**：Mermaid 图，分栏和连线沿用现在的，按五种颜色上色，节点上写卡片编号。
3. **卡片总表**：每张卡一行，列：编号、卡片、颜色、证据级别、一句话现状、链接。链接三个：摘要（跳到本文件该卡片的那一节）、交付物（文件夹）、测试报告（文件）。没有的写"无"。
4. **每张卡片一节**：用显式锚点（例如 `<a id="card-b01"></a>`），不要依赖 GitHub 按中文标题自动生成的锚点。内容顺序：一屏摘要（声称做到了什么、证据级别、测了什么、用什么数据、结果对比门槛、局限）；交付物和测试报告链接；完成标准；开始条件；做法；前置依赖与被谁依赖；待决事项（写明谁决定）；是否依赖 B04。

所有链接用相对路径，保证在 GitHub 上和本地编辑器里都能点。
