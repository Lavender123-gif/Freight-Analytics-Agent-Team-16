## 1. 复查指出的三个漏洞

1. 紧贴金额的负号（`-$20`、`$-20`）读成正数，静默通过；税行和 `UNSPECIFIED_AMOUNT` 同样。
2. 分隔符写法 `...-$69.00 DUE` 被读成贷记，也能通过，因为紧贴负号被当成了贷记依据。
3. 贷记词只要出现在证据短语里任何地方，就能支持另一笔金额读成贷记，例如 `CREDIT $10.00 WAS PAID; LIFTGATE $50.00` 把 50 读成 -50。

## 2. 改法（代码只核对，不推导正负号）

1. **贷记词必须是本金额的。** 每个金额的"本地范围"是：从前一个金额结束到后一个金额开始之间的原文（按数字表的位置）。贷记词只有落在本地范围里，才算这个金额的依据。不再用证据短语里的任意位置。
2. **三种依据**：本地范围里的贷记词（`rules.yaml` 贷记一类）、金额外面的括号、紧贴金额的负号。带空格的短横线（`- $18.00`）不是依据，也不触发任何标识，照旧当分隔符。
3. **规则：**
   - `is_credit` 为真，三种依据都没有：强制检查不通过，回给模型修改（现有规则 1，改用本地范围）。
   - 紧贴的负号，且本地范围里没有贷记词、也没有括号：这是"分隔符还是贷记说不清"的情况。**不论模型读成正还是负，都打 attention 标识送人工。**
   - `is_credit` 为假，但本地范围里有贷记词或有括号：打 attention 标识送人工（现有规则 2，改用本地范围）。
   - 只适用于计入的明细金额（费用、未指明金额、税，状态 CLAIMED 或 UNPAID），和 T23 的取舍一致。
4. **测试**：复查报告里的每个复现都写成测试（`LIFTGATE -$20.00`、`LIFTGATE $-20.00`、`TAX -$20.00`、`AMOUNT -$20.00` 读成正数；`...-$69.00 DUE` 读成负数和读成正数；`CREDIT $10.00 WAS PAID; LIFTGATE $50.00` 把 50 读成贷记），加上 T23 原有的正反例。每个测试断言结果：拒绝、送人工，或通过。
5. **重放**：在三份存档读法上（开发集全量、第三轮 mock、第四轮新增）分别统计：会被拒绝的、因紧贴负号送人工的、因本地贷记词或括号送人工的，各多少条，逐条列出。**开发集新增送人工超过 5 条就停下找我。**
