## 2. 第一部分：工作量重排

**2.1 重新估人时。**07 的估计没有说明是按什么方式写代码。本项目的代码是用 Claude Code 辅助写的，请按这个前提重新估每项任务的人时，并在文件开头写明这个前提。人工标注、和 Jake 沟通、展示这类不能交给 Claude Code 的工作，按人工估。

**2.2 分层。**把 07 的 33 项任务（可以合并或拆分，改动要说明）分成三层：
- **必须做**：缺了它，课程七条技术要求或 Jake 批准的范围就不满足；或者它在必须做的任务的依赖链上。每项写明它满足哪一条要求。
- **应该做**：明显提升质量，但缺了也能交付。
- **可以不做**：本轮放弃也不影响交付。

审核界面是已定的交付物（决定 1.8），放在"必须做"，但给出最小可用版的人时，以及更小的替代方案（例如只用开源工具配置）及其人时。

**2.3 和预算对比。**算出三层各自的总人时。以"组员 80 小时"为固定预算，算出：只做"必须做"时，用户本人需要承担多少小时；加上"应该做"时又是多少。不要替用户决定做到哪一层，给出两三个方案（例如"只做必须做""必须做加其中某几项"），每个方案写总人时、用户本人的小时数、放弃了什么、风险是什么，标"建议，待确认"。

**2.4 难度。**每项任务标技术难度，口径写在表前：
- **低**：不需要写代码，或照现成模板就能做。
- **中**：要写代码，但改动局限在一处，不需要理解整个架构。
- **高**：在关键路径上，或者要理解整个架构才能做。

**2.5 任务清单的写法。**每项写：编号、一句话说明做什么、所属层、人时（区间）、难度、需要的技能、依赖哪些任务和哪些 Jake 的问题、完成标准。**不写负责人，不写"建议谁做"，不按人分组。**只按流程环节或工作线分组。

**2.6 关键路径和时间线**按新的估计和方案重画（Mermaid）。今天是 2026-11-05；中期汇报暂按 2026-11-12、期末暂按 2026-12-03，都标"待确认"。

**2.7 一处要按决定记录改正。**07 计划第 6 节风险 1 写的是"多 PK 先当导出复制、只做提示"，06 报告也说 J1 的回答决定"提示还是标红"。这和决定 5.3 冲突：后面的每一份都标红、由审核员判断，不因 J1 的回答改变。新计划按决定 5.3 写。06 报告里的那句话不改，在新计划的"和旧文档的差异"里列出。

## 3. 第二部分：精炼报告

写一份给用户本人先读的报告，**精炼程度相当于一份 10 页的幻灯片**：
- 十节，顺序是：我们在做什么；现在在哪；11 月 4 日的决定；流程逐环节（每环节一行：做什么、状态、相关的 Jake 问题编号）；给 Jake 的问题（按环节分组，每个问题一行）；数据发现和 schema v0；任务清单摘要（按层、按工作线的人时和难度汇总，完整清单链接到第一部分的文件）；预算方案（第 2.3 节的方案对比）；风险；会上要定的事。
- 每节不超过半屏，能用表格就用表格，表格每格不超过一行半。全文控制在约两屏。
- 只写结论和数字，不写推导过程；推导留在第一部分的文件里，用链接指过去。
- 不出现任何人名的任务分配。
