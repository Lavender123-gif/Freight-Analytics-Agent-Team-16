# 任务：把我们的费用代码表对到 Jake 的清单上，看落下多少，给出方案建议

日期：2026-11-13
编号：按仓库现有约定取下一个任务编号。

## 0. 背景和目的

Jake 发来了一份费用清单（Addenda B Accessorial List，每行是一个名称加一个 EDI 代码，没有定义）。我们自己有一份费用代码表（每个代码带定义和数据里的写法示例）。

Zizhang 的方向是：**优先用 Jake 的清单做根**。只有在它明显不如我们自己的单子时才保留我们的。

这一轮要回答三个问题：

1. 我们的代码往 Jake 的清单上对，能对上多少。
2. 以 Jake 的清单为根、把我们的定义和写法示例挂上去之后，开发集里的费用有多少落在清单之内，落下的是哪些。
3. 基于这些结果，你推荐哪种方案。

## 2. 要做的事

### 2.1 把 Jake 的清单整理成表

1. 从 PDF 抽出"名称、EDI 代码"两列。报告总行数。
2. 记录抽取时的异常：没有代码的行、跨行的条目、明显的拼写问题。只记录，不修正原文。
3. 按名称去重。报告不重复的名称有多少个，哪些名称对应多个代码（列出名称和代码数）。

### 2.2 把我们的代码对上去

以仓库里当前的 `taxonomy.yaml` 为准（不是任务书里的任何描述）。对每一个代码，给出：

- 对到 Jake 清单里的哪个名称（或哪几个）。
- 对应关系的类型，五选一：
  - 完全对应；
  - 近似对应（说明差在哪）；
  - 一对多（Jake 的清单里有多个条目都能放，列出来）；
  - 只能作为子项挂在某个条目下面（Jake 的条目更宽，例如 PT 挂在运费下面）；
  - 没有位置。
- 一句理由。按含义判断，不要只靠字面匹配。

对"没有位置"的代码，另给一个建议：挂到哪个最近的上级下面，作为标明"非清单原有"的扩展项；或者说明为什么哪里都不该挂。

### 2.3 用数据量一下覆盖

用已保存的开发集全量读法（最近一次留存的版本，写明是哪一次）。每笔被计入的费用都有我们的代码，通过 2.2 的对应关系折算到 Jake 的清单上。

按**出现次数**和**金额**各报一遍，分成五类：

1. 落在完全对应或近似对应的条目上；
2. 落在一对多的条目上（清单里有位置，但不唯一）；
3. 落在子项上（挂在 Jake 的某个条目下面）；
4. 落在扩展项上（清单里没有位置）；
5. 现在就归在"其他"里的。

对第 5 类单独做一步：列出"其他"里不重复的费用写法，带出现次数和金额。逐个判断 Jake 的清单里有没有合适的条目能接住它，给出条目名称和一句理由。汇总：Jake 的清单能把"其他"吸收掉多少。

### 2.4 反过来看 Jake 的清单

清单里没有被 2.2 和 2.3 用到的名称有多少个。粗分成两组并各给数量：

- 明显与这批数据无关的运输方式或环节（如海运、空运、报关）；
- 公路整车和零担可能用得上、但开发集里没出现的。第二组列出名称。

### 2.5 做一份"Jake 的清单加定义"的草稿

先看 2.3 的数字。如果你判断覆盖不好，草稿可以只做到骨架，并在结论里写明判断依据和原因。否则做完整草稿：

- 每个条目一行：Jake 的名称（作为根）、它名下的全部 EDI 代码、对应的我们的代码、定义、数据里的写法示例。
- 定义和写法示例从我们的单子带过来。
- Jake 独有的条目里，只有在 2.3 第 5 类中接住了数据写法的那些，由你起草一句定义并标明"CC 起草"。其余的定义留空。
- 子项和扩展项单独标出，写明挂在哪个条目下面。
- 每个条目标一个相关度：被我们的代码用到；接住了"其他"里的写法；公路运输可能用得上；与这批数据无关。

这只是草稿，不替换 `taxonomy.yaml`。

### 2.6 给出方案建议

列出你认为可行的方案（至少包括：保留我们的单子并补上 EDI 对照；以 Jake 的清单为根；两者之间的折中，比如只保留相关的条目）。每个方案写：

- 提示词和代码表要怎么变；
- 需要重跑什么，预计花费；
- 你看到的风险。

给出你推荐的一个，并写明下一步怎么用模型验证它（设计和预计花费），**但这一轮不要跑**。

判断口径：没有明显差别时用 Jake 的清单。
