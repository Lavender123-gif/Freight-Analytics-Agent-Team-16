# 任务 03：项目状态看板、流程图更新、绿色模块的可展示交付物

## 0. 执行方式与硬约束

- 先读本任务书和仓库根目录 `CLAUDE.md`，进 plan mode 出执行计划，等我批准后再动手。
- 本任务书编号如果和 `docs/tasks/` 里已有编号冲突，按现有顺序顺延改名，并在最终报告里说明。
- 不调用任何 LLM API，不用 API 额度。
- 不打开测试集，不读原始 Excel。所有运行只用开发集 `data/processed/dev.csv`、合成用例、`scratch/` 下已有脚本。

- 所有输出只落在仓库内。
- 脱敏沿用 01、02 报告的约定：会进版本库的文件里，人名写 `[PERSON]`，邮箱写 `[EMAIL]`，不出现 shipment 号、发票号、PK、承运商代码，承运商按"最大承运商"等描述称呼。行级输出只写到 git-ignored 的 `data/interim/deliverables/`。

## 4. 看板：每张卡片下面写什么

看板文件开头放一张 Mermaid 流程图（GitHub 能直接渲染），按上表分六栏、按处理顺序连线，用 `classDef` 给四种颜色上色。图下面每张卡片一节，固定这几项：

1. **是什么**：一两句话，组员不读其他文件也能看懂。
2. **现状与依据**：现在做到哪，依据是哪个文件、哪个脚本、哪次运行。
3. **交付物**：绿色卡片写 `docs/deliverables/` 里对应文件夹的路径和一句话概括；非绿色卡片写"变绿需要什么交付物"。
4. **开始条件**：什么前提满足了才能动手，引用卡片编号。例如 D1 什么情况下可以迁入 `src/`。
5. **做法**：高层步骤，3 到 6 步，讲清楚怎么做，不写到代码细节。
6. **前置依赖 / 被谁依赖**：卡片编号列表。
7. **待决事项**：每项写清楚由谁决定（我、客户、团队）。不要替我决定。已知的一项：B04 第 3 步用什么后端调用模型还没定（我的规则是 Claude Code 只走订阅、不用 API 额度；流水线逐条调用模型的后端方案未定），写进 B04 的待决事项。
8. **完成标准**：什么状态算变绿。

第 4 到 8 项的内容，只能来自 02（尤其第 9、10 节）、01、01b、`CLAUDE.md` 和代码。每一条后面标来源（例如"02 §9.4"）。来源里找不到、是你自己的建议的，标 `[建议，待确认]`。

看板文件头部写：最后更新时间、更新它的任务名。

## 5. 绿色卡片的交付物

每张绿色卡片在 `docs/deliverables/<编号>-<短名>/` 下有一个独立、可以单独拿出来展示的交付物，包含：

- `README.zh.md` 和 `README.en.md`：这一块做什么；输入和输出；一条命令复现；用了什么检验数据（开发集全量、合成用例，或与 01、01b 已知数字对照），并写明不是测试集；结果（数字、通过与否）；局限（例如样本内结果）。
- 结果文件：汇总表、计数、通过与否。只放汇总或脱敏后的少量例子（3 到 5 条，展示处理前后），行级结果放 `data/interim/deliverables/`。
- 复现脚本放 `scratch/deliverables/`，README 里写运行命令。

先盘点：每张绿色卡片现在有没有满足上述要求的交付物。已有的整理进对应文件夹（复制，不移动原件）。没有的，用已有脚本和开发集补做。补不出来的，按第 0 节处理，并把卡片改成黄色，写明缺什么。

## 7. 写进 CLAUDE.md 的长期规则

在仓库根目录 `CLAUDE.md` 加一节"收尾检查"，以后每个任务结束前都执行：

1. 检查本任务影响到的卡片，更新 `docs/status/project_status.zh.md` 和 `.en.md` 的颜色、现状、做法、待决事项，更新文件头部的时间和任务名。
2. 本任务改动了流程结构的，更新 `docs/status/flow_src/` 并重新生成两版流程图。
3. 卡片变绿时，`docs/deliverables/` 里必须同时有它的交付物，否则不能标绿。
4. 中英两版在同一次任务里一起更新，以中文版为准。
5. 最终回报里列出：哪些卡片变了、从什么变成什么、为什么；没有变化也要写明"状态文件已检查，无变化"。
