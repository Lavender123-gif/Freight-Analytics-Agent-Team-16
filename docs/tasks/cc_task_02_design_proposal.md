## 四、当前的设计决定

### 4.1 产品层面：程序回答什么、做什么动作

**内容层**：对每条争议回答三个问题：
1. 承运商这次要多少钱：文本主张的金额，以及它和 Delta、和同一票货更早记录的关系
2. 这些钱分别为了什么：line items，每项有金额、费用代码、原文出处
3. 承运商声称的理由和依据：明确标为"承运商声称"

**动作层**：在内容层之后，三个不同层级的动作：
1. **Flag**：局部标识，挂在 JSON 里的某个具体对象上。凡是能检测到的异常都要标记。它本身不决定记录去哪里。
2. **转人工**：整条记录层面的决策。做不了、不确定、超出权限的都转人工。由规则根据 flag 计算，LLM 不决定。
3. **打回**：大部分在转人工之后由审核员决定，系统只提供草稿（理由、要改什么、改到什么程度算合格）。只有离谱且代码能确定的情况可以自动打回：文本为空，或只有数字没有文字；并且同一票货更早的记录里没有 Delta 相同、带完整说明的记录（只查更早的，不查之后的）。审核员在审核后记录问题归属，系统不在 flag 阶段指定归属。

**范围**：不判断该不该付款。"自动通过"一类的说法只能指"拆分结果可信"，不能暗示付款。

**承运商管理的数据基础**：flag、转人工的原因、审核员的决定和归属、承运商的重提，都要能被记录下来，即使本项目不做相关功能。

### 4.2 术语

- **诊断**：某一步发现问题的那一刻生成的记录，带类型、位置（指向 JSON 里的哪个对象）、证据。它是中间状态。
- **Flag**：第 6a 步把所有诊断汇总、去重、按配置赋予严重程度之后的结果。

**错误类型以 JSON 中的对象为单位组织**，像 Python 的异常类一样有层级：比如"数字"对象可能出现哪些错误、"line item"对象可能出现哪些错误、"记录"对象、"与同一票货其他记录的关系"对象各自可能出现哪些错误。"在哪一步发现的"只是每条诊断的一个属性，不是分类依据。

### 4.3 流程（v3）

| 步骤 | 做什么 | 由谁做 |
|---|---|---|
| 0-1 读入与门控 | 一行一个记录对象；按（shipment、Event Date、文本、Invoice Amount、Delta）去掉导出造成的完全重复；脱敏（人名替换为 `[PERSON_n]` 占位符，保留句子结构）；注入检查 | 代码；脱敏拟用 Presidio |
| 2 数字识别与标准化 | 找全文本中的每个数字并编号，记录原文写法、标准化值、位置、客观特征（前面是否有 `$`、紧跟的单位词、是否由空格合并）；**不判断数字的身份**；覆盖检查：任何未被认领的数字字符标为未识别区域 | 代码，自己写规则 |
| 3 理解 | 单一模型，带工具的 agent 循环 | LLM |
| 4-5 提交检查 | 在提交工具内部：结构校验和业务检查 | 代码 |
| 5.5 历史检查 | 只读同一票货中 Event Date 严格更早的记录，同一分钟的互相不可见；比对金额与更早某版 Delta 相等、约 1.05 倍、同额换名、文本相同等 | 代码 |
| 6a 汇总 | 诊断变成 flag | 代码 |
| 6b 处置规则 | 按规则配置计算是否转人工、是否属于可自动打回的情况 | 代码，规则在配置文件里 |
| 6c 打回 | 自动打回走模板；转人工的记录生成打回草稿 | 代码生成草稿，人决定 |
| 7 输出 | Record、Excel 导出、事件日志 | 代码 |

### 4.4 数据模型的已定部分

- 每个数字用三个独立字段描述：`kind`（这个数字是什么：费用金额、性质未说明的金额、税额、合计、费率、数量、参考信息等）、`status`（它在这次争议中的状态：本次主张、已开票、已付、未付、扣减、无）、`charge_codes`（费用代码列表，可为空、一个或多个；多个即合并金额）
- 对账统一成一条规则：`status` 为"本次主张"或"未付"的数字之和应等于 Delta；若有 `kind` 为合计的数字，它也应等于这个和
- 每个判断带原文支撑短语，代码核对它确实出现在原文中（精确匹配失败后，做容忍空格和大小写差异的匹配）
- line item 有原因片段和依据类型（已通知 PPG、按 PPG 清单、按合同、无）
- 未识别区域的解读是唯一允许模型写数字的地方，代码用"只留数字字符"做精确比对
- 输入给 LLM 的是固定结构的 JSON：脱敏原文、带编号标记的文本（标记里保留原文写法，如 `[#2 $15]`）、编号表、未识别区域、Delta、Delta 正负、省份。**这个结构就是白名单**：`Dispute Status` 严禁进入；`Reason Code` 和 `Carrier` 不进入

**你来决定并论证**：是否还需要 `dispute_type` 这类记录级分类字段。你在 P17 里提出过"处理路径分类"，理由是决定用哪条对账规则；但对账已经统一成一条规则。请重新论证它还有没有用途；没有就不要。

### 4.5 第 3 到 5 步内部每一轮的产出

| 这一轮 | 得到什么 | 是否存进记录对象 |
|---|---|---|
| 模型查税率、查示例、试算对账 | 工具结果 | 不存，只写日志 |
| 模型报告没把握 | 一条诊断 | 存 |
| 提交，检查不通过 | 修复回执：错在哪个对象、什么类型、证据、允许怎么改 | 不存，退回给模型 |
| 提交，检查通过 | 内容层答案，以及检查中发现的、不需要模型修改的诊断 | 存 |
| 重试用完仍不通过 | 最后一次答案标记为"未通过"，加一条严重诊断 | 存 |

**退回还是只记录**：只有模型改答案能解决的问题，才退回给模型（格式错误、编号不存在、代码不在列表、支撑短语找不到、计入 Delta 的金额之和对不上）。数据本身的问题只记录，不退回（文本自带算式不成立、Delta 恰为合计两倍、税额与税率表不符、历史检查的发现）。退回这类问题只会诱导模型凑数。每种诊断类型都要明确属于哪一类。

重试上限暂定 2 次。

### 4.7 其他已定事项

- 假设 H1：Delta = Invoice Amount − Shipment Amount，每条争议对应独立的发票版本。H2：文本金额与 Delta 同币种（待确认）
- Delta 的正负是结构属性，不是类型：为 0 时没有对账锚点，为负时是承运商少收
- Reason Code 不可信：不进入 LLM；只在它与模型判断属于两个不同的具体类别时产生诊断
- taxonomy 以行业标准为骨架（X12 210 运费发票的 L1 段费用代码、project44 的附加费参考代码、承运商公开价目表），数据用于验证覆盖和挑选，不从数据里穷举；标准里没有的收费作为某大类下的扩展项；极少出现的归为 OTHER 并保留原文短语；P12 那类费用给一个"含义待确认"的独立代码
- v1 只用单一模型。"同一模型跑三次"不进入 v1 的规则；"操作方加审核方"的双模型设计留作以后的实验，方案里留出位置即可
- 规则、阈值、严重程度都写在配置文件里，不写死在代码里
- flag 代码带对象类别前缀，每个代码配一段固定说明：触发条件、证据格式、退回还是只记录、给审核员的建议、给承运商的修改要求、合格标准。打回通知模板取自这段说明
- 人名清单 `person_tokens.txt` 不作为运行时的匹配名单（那等于用开发集的答案应付开发集），只作为测试脱敏漏检率的标准答案
