# PPG 运费争议文本拆分：当前流程设计

版本：2026-10-20 讨论稿

---

## 一、设计原则

1. **Baseline**：每条记录直接交给 LLM，配一段认真写的 prompt，不加任何工程。在这份数据量下成本不构成约束，所以我们做的每一项技术选择，都必须在准确性、稳定性、安全性或可审计性上比 baseline 更好，并且能讲出理由。
2. **不允许静默错误**：每一种错误，要么在运行时被发现，要么它的发生率在离线评估里被测出来。一个不完美的组件（比如只能解决 95% 的库）可以接受，前提是它的失败能被明确识别，并把所需信息交给 LLM。
3. **我们在覆盖率上一定比 baseline 差**：baseline 对每条记录都给答案，我们会转人工、会打 flag。卖点不是"答对的更多"，而是"自动通过的部分错得更少，错的部分会被暴露出来"。
4. **LLM 负责理解，代码负责其他一切**：计算、校验、调度、flag 生成都由代码完成，规则每次都一样。
5. **按单条记录处理**：不论请求是陆续来的，还是一批导出做事后分析，处理单位都是一条记录，保证每条的处理口径一致。

## 四、运行前准备的知识资产

全部放进 skill 文件夹，客户以后可以自己维护。

### K1. Taxonomy（费用代码表）

LLM 的**可选答案列表**，不用于关键词匹配。

| 列 | 内容 | 用途 |
|---|---|---|
| `code` | 如 `LIFTGATE` | LLM 只能从这一列选 |
| `definition` | 一句话定义 | 让 LLM 按定义判断，不按字面 |
| `phrasings` | 数据里见过的写法，如 TAILGATE、LIFT GATE | 放进 prompt 作参考，帮助识别缩写和拼写错误 |
| `x12_code` | 对应的行业标准代码（如有） | 说明口径有行业依据 |

构建步骤：

1. 行业种子：X12 accessorial 代码表、承运商公开的费用清单
2. 从开发集挖短语：金额前的短语截出、标准化、按频次排序
3. LLM 离线映射短语到候选代码，人工逐条审核，删掉没出现的，补上缺的
4. Jake 确认粒度，冻结为 v1，带版本号

永远保留一个 `OTHER`，选它时必须带出原文短语。落进 `OTHER` 的比例就是覆盖率指标。

### K2. 争议类型和允许的数字角色

| 类型 | 含义 | 判定方式 | 允许的数字角色 |
|---|---|---|---|
| A 补收附加费 | 要加一笔额外服务费 | LLM | 索赔项、税、文中合计、参考信息 |
| B 费率争议 | 费率算错，Delta 是两个费率之差 | LLM | 费率依据、声称的差额、参考信息 |
| C 追讨欠款 | 讲付款历史 | LLM | 已开票、已付、未付、**扣减**、参考信息 |
| D 结案或状态 | 记录结果 | 代码：Delta ≤ 0 | 不抽取 |
| E 无信息 | 只有数字或空白 | 代码：没有文字内容 | 不抽取 |
| OTHER | 不属于以上任何一类 | LLM | 不抽取，转人工 |

"扣减"是用例子走流程时发现缺失后补上的（"ADJUSTED OFF 150.00"）。

### K3. 对账规则（每种类型一条）

| 类型 | 规则 |
|---|---|
| A | 索赔项 + 税 = Delta；文中合计（如有）应等于这个和 |
| B | 声称的差额 = Delta；没有差额时无法对账，打"需对照合同" |
| C | 未付 = Delta |

### K4. 税率表

加拿大各省 GST/HST 税率，来自公开资料。

### K5. 示例库

从**开发集**人工标注 50 到 100 条，按类型分层，覆盖尾部写法。不碰测试集。留一承运商验证时，被留出承运商的示例一并移除。

### K6. SKILL.md

K1 到 K3 的定义、判断规则、输出要求，按类型分节，写成 LLM 读的操作规程。

## 五、逐条流程

### 总览

| 步骤 | 名称 | 由谁做 | 一句话 |
|---|---|---|---|
| 0 | 读入 | 代码 | 拆成一行一个记录，取字段 |
| 1 | 入口门控 | 代码 + 本地 NER 模型 | 去重、脱敏、注入检查、D/E 类分走 |
| 2 | 数字识别与标准化 | 代码 | 找全、标准化、标格式、覆盖检查 |
| 3a | 类型分类 | LLM，独立调用三次 | 判定 A、B、C 或 OTHER |
| 3b | 按类型抽取 | LLM + 工具 | 按该类型指令给每个编号定角色和代码 |
| 4 | 格式校验 | 代码，在提交工具内部 | 不合法退回 3b |
| 5 | 文本对账 | 代码，在提交工具内部 | 对不上退回 3b，再不行退回 3a 一次 |
| 6 | 检查和定性 | 代码 | 统一生成所有 flag，定最终状态 |
| 7 | 输出 | 代码 | 存 Record，导出 Excel |

### 第 0 步：读入（代码）

只做一件事：把 Excel 拆成一行一个记录对象，取需要的字段，生成 `record_id`（文件名加行号）。

需要理解的只有 `Descritipion`，其他列是干净的结构化字段，原样使用：

| 列 | 怎么用 | 在哪一步用 |
|---|---|---|
| `Descritipion` | 要理解、要处理 | 1 到 3b |
| `Delta` | 原样使用，文本对账的标准答案 | 5 |
| `SHIPMENT_GID`、`Event Date` | 判断重复 | 1、6 |
| `Destination State`、`Source State` | 判断国家和省份，查税率 | 3b、5 |
| `Reason Code` | 只存着，第 6 步和模型判出的类型交叉比较，**不给 LLM 看** | 6 |
| `Carrier` | 不作为处理输入，只用于评估和导出 | 评估、7 |
| `Dispute Status` | **严禁使用**：是 PPG 的审核结论，给模型看会越界做付款判断，评估时也等于偷看答案 | 无 |
| 其他列 | 不进记录对象，第 7 步导出时按 `record_id` 关联回去 | 7 |

数据层面的已知事实：

- `PK` 不唯一（1,347 行只有 760 个），不能当主键
- `US/CAN` 全部填 US，但 1,174 行目的地是加拿大省份，此列弃用，国家和省份从地址字段判断
- 9 行文本为空，第 1 步归为 E 类

### 第 1 步：入口门控（代码 + 本地 NER 模型）

| 子步骤 | 做什么 | 结果去向 |
|---|---|---|
| 完全重复去重 | shipment 号、事件时间、原文、Delta 全部相同的只留一条，记录重复次数 | 重复的移除 |
| 脱敏 | 正则去邮箱电话；本地 NER 模型识别人名，替换成 `[PERSON_1]`。对照表只存本地，导出时还原 | 脱敏文本写入记录 |
| 注入检查 | 找指令式句子，只记录结果 | 第 6 步生成 flag |
| 规则预分类 | Delta ≤ 0 判 D 类；没有文字内容判 E 类 | D、E 直接到第 6 步；其余到第 2 步 |

NER 的风险：数据全是大写，NER 依赖大小写识别人名。对策是先转首字母大写再识别，加句式规则补漏（如 "CONFIRMED BY"、"FROM PPG" 后面的词），在开发集上测漏检率。

语义重复（同一 shipment、同一 Delta、文字不同）不在这里处理，作为第 6 步的检查项。

### 第 2 步：数字识别与标准化（代码，自己写的规则）

选择自己写规则而不用 Recognizers-Text 库的理由：覆盖检查对两者同样适用，抵消了库"能处理没见过的格式"这个优势；库在这份数据上认不出空格千分位、会拆碎时间戳，最终还是要自己补规则；Python 版本是 alpha，有依赖冲突；自己的规则二三十行加测试，客户能读懂能修改。

四件事：

1. **屏蔽日期时间**，避免被拆成多个数
2. **找全并标准化**：每个数字编号，记录值、原文位置、格式提示

   | 格式 | 例子 | 标准化 |
   |---|---|---|
   | 普通数字 | 300.00、$15 | 300.00、15 |
   | 空格千分位 | $ 8 400.00、1 684.68 | 8400.00、1684.68，标"空格合并" |
   | 点开头小数 | .68 | 0.68 |
   | 百分比、带单位数量、日期 | 124.2%、20 000 LBS、3 DAYS | 标对应格式提示 |

3. **覆盖检查**：原文里任何一个数字字符，如果没有被规则认领，就标为"未识别区域"。这一步不依赖规则本身的判断，所以漏掉的一定能被发现
4. **生成两样东西**：
   - 编号表，存在记录对象里，供代码校验用（位置是给代码用的）
   - 带标记文本，给 LLM 看，如 `SHORT PAID [#1 300.00] ... [#3 1684.68，原文 "1 684.68"，空格合并]`；未识别区域标为 `[未识别 ...]`

未识别区域交给 LLM 解读时，模型给出的数值要和原文做"只留数字字符"的精确比对（"8400.00" 与 "$ 8 400.00" 都化为 "840000"），一致才接受。

### 第 3a 步：类型分类（LLM，独立调用三次）

| | |
|---|---|
| 输入 | 系统指令：A、B、C、OTHER 的定义和例子。用户内容：带标记的文本、Delta |
| 输出 | 类型 + 原文中支撑判断的短语 |
| 代码检查 | 支撑短语必须出现在原文里；比较三次结果 |

| 三次结果 | 去向 |
|---|---|
| 一致，不是 OTHER | 进 3b，只带该类型的指令 |
| 不一致 | 按多数进 3b，记录"类型不确定" |
| OTHER | 转人工，到第 6 步 |

分类独立成一步的理由：抽取时只给模型该类型的指令和角色，任务更窄；分类准确率可以单独评估；可以做"分类与不分类"的对照实验；对账失败时可以明确退回重判。

### 第 3b 步：按类型抽取（LLM + 工具）

| | |
|---|---|
| 输入 | SKILL.md 中该类型那一节、带标记的文本、编号表、Delta、省份 |
| 输出 | 对每个编号：角色、费用代码（如适用）、原文支撑短语；原文提到但没给金额的项（如只写 "+ HST"）只标类型，金额由代码按税率推算并标为"推算" |
| 规则 | 模型输出里不写任何金额，只引用编号；可报告"解析可疑"（如 #3 和 #4 应为同一个数），但不能自己改编号表 |

工具（每个对应一个失败点）：

| 工具 | 作用 | 对应失败 |
|---|---|---|
| `submit_line_items` | 提交的唯一出口，内部执行第 4、5 步 | 金额编造、格式错误、越界输出 |
| `reconcile` | 提交前试算某种解读能否对上 Delta | 歧义解读、算术错误 |
| `lookup_tax_rule` | 按省份查税率 | 算术错误、"+ HST" 无金额 |
| `find_similar_examples` | 从示例库检索相似案例 | 尾部理解。**价值是假设，需实验证明** |
| `escalate_to_human` | 主动放弃并说明原因 | 不确定时的出口 |

taxonomy 只有几十个代码，直接写进 prompt，不另设查询工具。

### 第 4 步：格式校验（代码，在 `submit_line_items` 内部）

检查：结构完整；每个编号存在且恰好一个角色；角色是该类型允许的；金额类角色没有分给日期或百分比；费用代码在 taxonomy 里或为 `OTHER` 带短语；支撑短语出现在原文里。

不通过：错误退回模型，最多 2 次；仍不通过转人工。

### 第 5 步：文本对账（代码，在 `submit_line_items` 内部）

按 K3 中该类型的规则，用理解出的金额和 Delta 比较，容差一分；有税时用税率表检查税额。

| 结果 | 去向 |
|---|---|
| 对上 | 第 6 步 |
| Delta 恰好是合计的两倍 | 不重试，记录"Delta 双倍"，第 6 步 |
| 对不上 | 只返回事实（"你的加总为 X，Delta 为 Y"），不给提示。退回 3b，最多 2 次；仍不行退回 3a 重新分类，**只一次**；还不行，记录"对账失败"，第 6 步 |

每条记录记下提交次数。重新分类限一次，防止在类型之间来回跳，碰巧凑出能对上的组合。

### 第 6 步：检查和定性（代码）

所有记录在此汇合，所有 flag 只在这一步生成。

| Flag | 触发条件 |
|---|---|
| `SUM_MISMATCH` | 文本对账最终没对上 |
| `DELTA_DOUBLE` | Delta 是合计的两倍 |
| `TAX_INCONSISTENT` | 税额与税率表不符 |
| `NEEDS_CONTRACT_CHECK` | B 类 |
| `UNMAPPED_PHRASE` | 有费用归为 `OTHER` |
| `TYPE_UNCERTAIN` | 3a 三次结果不一致 |
| `TYPE_WITHOUT_AMOUNT` | 有类型但没有数字 |
| `PARSE_SUSPECT` | 模型报告解析可疑 |
| `POSSIBLE_DUPLICATE_CLAIM` | 同一 shipment、同一 Delta、文字不同 |
| `REASON_CODE_MISMATCH` | 模型判出的类型与 `Reason Code` 不一致 |
| `INJECTION_SUSPECT` | 第 1 步发现指令式文本 |
| `NO_EXPLANATION` | E 类 |
| `STATUS_ONLY` | D 类 |

非 flag 的可见提示：空格合并出的数字未参与对账验证；重新解读后才对上。

最终状态三选一：**自动通过**（无 flag）、**需人工查看**（有 flag）、**系统放弃**（转人工）。

### 第 7 步：输出（代码）

- **Record**：按 schema 存储，附 taxonomy、prompt、模型的版本号
- **Excel 导出**：表一每条记录一行（还原人名的原文、类型、费用摘要、状态颜色、flag、提示，并按 `record_id` 关联回原始各列）；表二每个 line item 一行

## 六、调度规则

调度器是代码，规则固定。LLM 只在两处做选择：3a 选类型，3b 决定调用哪个工具、是否主动放弃。

"出了问题"的信号来源，按可靠程度：

| 来源 | 例子 | 可靠程度 |
|---|---|---|
| 外部校验 | 对账失败、格式不合法 | 最高 |
| 多次运行的分歧 | 3a 三次结果不一致 | 中等 |
| 模型自我报告 | 调用 `escalate_to_human` | 最低 |

| 步骤 | 信号 | 去向 |
|---|---|---|
| 1 | 完全重复 | 移除，记录次数 |
| 1 | Delta ≤ 0 | D 类，到第 6 步 |
| 1 | 没有文字 | E 类，到第 6 步 |
| 1 | 指令式文本 | 记录，继续 |
| 2 | 有文字无数字 | 仍进 3a |
| 3a | 一致且非 OTHER | 3b |
| 3a | 不一致 | 按多数进 3b，记录 |
| 3a | OTHER | 转人工，第 6 步 |
| 3b | 主动放弃 | 转人工，第 6 步 |
| 4 | 不合法 | 退回 3b，最多 2 次；仍不行转人工 |
| 5 | 对上 | 第 6 步 |
| 5 | 双倍 | 记录，第 6 步 |
| 5 | 对不上 | 退回 3b 最多 2 次 → 退回 3a 一次 → 记录失败，第 6 步 |

重试次数（3 次分类、2 次重提交）目前是拍定的，看实验结果调整。

## 七、记录对象逐步填写

每一步只读前面写好的字段，只写自己负责的字段。出错时看哪个字段错，就知道是哪一步的责任。

| 字段 | 写入步骤 |
|---|---|
| `record_id`、原文、Delta、shipment 号、事件时间、省份、Reason Code | 0 |
| 去重结果、脱敏文本、注入检查结果、预分类 | 1 |
| 编号表、带标记文本、未识别区域 | 2 |
| `dispute_type`、三次分类结果 | 3a |
| 每个编号的角色、代码、支撑短语；推算项 | 3b |
| 校验结果、对账结果、提交次数 | 4、5 |
| flag、提示、最终状态 | 6 |
| taxonomy、prompt、模型版本号 | 7 |

## 八、静默错误清单

| 步骤 | 可能的静默错误 | 运行时如何发现 | 离线如何测 |
|---|---|---|---|
| 1 去重 | 不同争议被误删 | 记录每次删除 | 抽样核对 |
| 1 脱敏 | **人名漏掉被发出** | 很难 | 开发集人工标人名，测漏检率 |
| 1 脱敏 | 业务词被误删 | 被替换词紧挨金额时记录 | 测误删率 |
| 2 数字 | 漏掉 | 覆盖检查 | 无需 |
| 2 数字 | 认出但认错（合并、拆分） | 部分靠文本对账 | 开发集人工标注每个数字，测正确率 |
| 3a 类型 | 判错 | 三次不一致；对账失败 | 三次一致判错且碰巧对上的，gold set 测 |
| 3b 角色 | 判错 | 文本对账 | 假匹配率 |
| 3b 代码 | **费用代码判错（对账无感）** | 拟议：3b 多次运行比较；独立调用检查"短语是否符合代码定义" | gold set 测代码准确率 |
| 5 对账 | 错误解读碰巧对上 | 记录提交次数 | 假匹配率 |
| 6 定性 | 该打的 flag 没打 | 无 | gold set 对照 |

## 九、例子：SHORT PAID 300.00 ADJUSTED OFF 150.00 BILLED LINEHAUL 1 684.68

假设 Delta = 300.00，省份 AB。

| 步骤 | 发生了什么 |
|---|---|
| 0 | 拆出这一行，取字段，生成 `record_id` |
| 1 | 不重复；NER 未发现人名；无指令；Delta > 0 有文字，需进 LLM |
| 2 | #1 = 300.00（11–16），#2 = 150.00（31–36），#3 = 1684.68（54–61，空格合并）；覆盖检查通过 |
| 3a | 三次均判 C，支撑短语 "SHORT PAID"，存在于原文 |
| 3b | #1 未付（SHORT PAID）；#2 扣减（ADJUSTED OFF）；#3 已开票，代码 LINEHAUL（BILLED LINEHAUL） |
| 4 | 全部合法 |
| 5 | C 类：未付 300.00 = Delta 300.00，第 1 次提交通过 |
| 6 | 无 flag；#3 空格合并未经对账验证，加可见提示；状态：自动通过 |
| 7 | 存 Record，导出 Excel |

若 3b 把 #3 判为未付：1684.68 ≠ 300.00，退回重提交。

## 十、相对上一版架构的变更记录

| 变更 | 理由 |
|---|---|
| 删除字典匹配和快速路径 | 原本为省成本；成本不构成约束后没有对应的失败点。字典中有用的部分转为 taxonomy |
| 语义分类独立成 3a，D/E 由代码判定 | 见 3a；能用规则判定的不交给 LLM |
| 数字识别用自己写的规则 + 覆盖检查 | 见第 2 步 |
| Delta 一致性检查移到文件级 | 它能捕捉的失败（文件被手改、导出模板变化）是文件级问题，不是单条记录问题 |
| flag 统一在第 6 步生成 | 标准统一 |
| 示例库只来自开发集 | 原设计从 gold set 检索，会造成测试集泄漏 |
| 对账按类型区分，记录提交次数 | 不同类型的数字含义不同；区分"一次对上"和"多次才对上" |
| C 类角色新增"扣减" | 走例子时发现缺失 |

## 十一、待办和未决

1. Delta 是否由 OTM 自动计算
2. `Invoice Dups Removed` 的含义，以及去重口径
3. 18 行 Delta 恰好是文中合计两倍的原因（多为 CFFO）

5. 审核员是否需要看到"理由或证据"（如 "AS PER LIST FROM PPG"），决定是否单独存字段
6. 税率按目的地省份还是起运地省份

### 设计未定

1. `find_similar_examples` 是否保留；若删除，工具数降为 4，需重新面对课程"至少 5 个"的要求（宁可少，不凑数）
2. 本地 NER 模型选型，以及大写文本下的漏检率能否接受
3. 费用代码错误的两种运行时检测办法是否采用
4. B 类的角色清单细化，需看完全部 B 类样本
5. 重试次数和分类次数的取值

### 需要实验确认

用同一个实验回答：从开发集抽 50 行，baseline 和本流程各跑一遍，人工看结果。

1. taxonomy 和类型清单的覆盖率（落进 `OTHER` 的比例），以及同一个词在不同上下文中能否区分
2. 文本对账作为检测器的误差：假匹配率、误报率
3. baseline 的稳定性：同一批数据跑两遍的一致率
4. 先分类与不分类的对照
5. 数字规则的正确率（需人工标注每个数字）
6. 脱敏漏检率

### 数据使用说明

本轮语义分析、覆盖率测试用的是全部 1,347 行，包括测试集。作为设计和选型依据影响有限，但这些数字不能作为最终评估结果报告。真正干净的检验依赖 Jake 的新数据。
