# v2 之后的设计修改

与 `ppg_pipeline_v2.md` 冲突时，以本文件为准。

## 假设

| 编号 | 内容 | 状态 |
|---|---|---|
| H1 | Delta = Invoice Amount − Shipment Amount，由系统计算，不做逐条核对 | 已采用 |
| H2 | 文本中的金额与 Delta 同币种；全部数据中几乎没有注明币种 | 待 Jake 确认 |

## Taxonomy 与 ontology

- 以行业标准为骨架：X12 210 运费发票的 L1 段费用代码、project44 的附加费参考代码、承运商公开价目表（如 Estes，即数据中的 EXLA）。
- 数据的作用是验证覆盖率和挑选需要的代码，不是从数据里穷举代码。
- 数据里出现、标准里没有的收费，作为某个标准大类下的"扩展项"并标记为非标准。
- 只出现极少次、标准没覆盖的（如 CV19 FEE），归为 `OTHER` 并保留原文短语，不算信息损失。
- 轻量 ontology 三层：同义层（多种写法指向同一概念）、层级（大类到具体项，模型拿不准时可退到大类）、属性（是否按数量乘单价、是否计税）。
- 注意"看似同义、实则不同"的概念：等候费、滞箱费、仓储费、集装箱日租。
- 待定：LUMPER/SORTATION 是一项服务还是两项。

## 争议类型

- E（无说明）和 OTHER（有内容但不属于已定义类型）**分开**：E 退回承运商补充说明，OTHER 交审核员阅读并作为扩展类型的候选。
- **Delta 的正负不是类型，是结构属性**：大于 0 正常；等于 0 表示没有对账锚点；小于 0 表示承运商少收。不能用 Delta ≤ 0 判定"结案"。
- 类型 v1 只作为理解步骤输出的一个字段，用途是给审核员提示该核实什么、给承运商分析做汇总。"先分类再抽取"作为实验组，只有证明在尾部记录上更准才改成两步。

## 数字的描述：两个维度加一个代码列表

原来的单一 `role` 字段把两个独立维度混在一起，已拆分：

| 字段 | 回答的问题 | 取值 |
|---|---|---|
| `kind` | 这个数字是什么 | 费用金额、性质未说明的金额、税额、合计、费率、数量、参考信息（单号、日期、地址、邮编） |
| `status` | 它在这次争议中处于什么状态 | 本次主张、已开票、已付、未付、扣减、无 |
| `charge_codes` | 是哪项费用 | taxonomy 代码列表，可为空、一个或多个；多个即合并金额 |

例：`ADJUSTED OFF 150.00 HAZMAT` 是 `kind`=费用金额、`status`=扣减、`charge_codes`=[危险品费]。

## 对账：统一成一条规则

- 不再按类型分别定规则。
- **`status` 为"本次主张"或"未付"的数字之和应等于 Delta**；若有 `kind`=合计 的数字，它也应等于这个和。
- Delta 等于 0 时无法对账，打 flag。

## 数字识别

- 用自己写的规则，不用 Recognizers-Text 库（库认不出空格千分位、会拆碎时间戳、Python 版本为 alpha 且有依赖冲突）。
- 外加覆盖检查：原文中任何未被规则认领的数字字符，标为未识别区域，交给 LLM 解读，模型给出的数值与原文做"只留数字字符"的精确比对。
- 识别这一步**不判断数字的身份**（金额、英里、地址），只记录客观特征：前面是否有 `$`、后面紧跟的单位词、是否由空格合并。身份由 LLM 判断。
- 给 LLM 的标记保留原文写法，如 `[#2 $15]`、`[#1 300.00]`，不显示标准化后的值。
- 覆盖率不等于正确率，正确率需要在开发集上人工标注每个数字来测。

## LLM 的输入输出

- 输入为固定 schema 的 JSON：`raw_text`（脱敏原文）、`marked_text`（带编号标记）、`numbers`（每个编号的原文写法、标准化值、客观特征）、`unrecognized`、`delta`、`delta_sign`、`province`。
- schema 即白名单：`Dispute Status` 严禁进入；`Reason Code`、`Carrier` 不进入。
- 每次调用的输入 JSON 原样存档，可重放。
- 输出通过提交工具的 JSON schema 强制：每个编号的 `kind`、`status`、`charge_codes`、`other_phrase`、`evidence_phrase`；每个 line item 的 `reason_text`（原因，原文片段）、`evidence_type`（已通知 PPG、按 PPG 清单、按合同、无）；整条记录的 `dispute_type`、`parse_suspects`、`unrecognized_reads`。
- 所有原文片段类字段由代码核对是否真的出现在原文中。除 `unrecognized_reads` 外，模型不写任何金额。
- 例：`BC ROAD CLOSURE ... FROM PPG NOTIFIED $8.39` 中，费用是道路封闭附加费，原因是道路封闭，依据类型是"已通知 PPG"。

## 提交工具的退回：修复回执

借鉴 Archify 的做法：校验或对账失败时，不只返回"错了"，而是返回稳定的错误代码、出错的具体位置、测量到的证据、以及允许的修复方式（比如只能改 `status`，不能改编号表），最多两轮修正。格式待定。

## Reason Code

- 假设由 PPG 填写，待确认。
- 不是标准答案：除燃油附加费外，专门代码很少使用，默认"其他附加费"。
- 不再做逐条不一致 flag（会产生大量噪音），只在两个具体类别互相矛盾时打 flag。
- 可作为给 Jake 的发现：按 Reason Code 统计会严重低估危险品费、等候费、装卸费。

## Key 的三层

| 层级 | key |
|---|---|
| 发票 | `PK`，可能为空 |
| 一次争议 | `record_id`，一行一个 |
| 一个 line item | `record_id` 加编号 |

返工率需要先定义"同一个 claim"，可能是发票号加费用代码之类的组合。

## 退回权限与承运商数据

- Agent 只能凭确定性信号自动退回：无说明、无金额、合并金额无法拆分。
- 需要理解才能得出的判断，必须经审核员确认才退回。
- 每次退回记录：谁决定的、依据哪个信号、承运商如何修改。
- 返工率 = 总提交次数 ÷ 不重复 claim 数，系统上线后积累；争议发生率需要 Jake 提供各承运商的运单总量。
- 能直接归因到承运商的信号：无说明、无金额或未写 `$`、非标准术语、同一票货多次争议。对账失败、类型不一致、重试次数多反映的是系统难度，不直接用于评价承运商。
- `Dispute Status` 不进入模型，但可作为事后统计的结果数据（如某承运商某类费用的被拒比例）。
- 给 PPG 付款建议：暂不做。后期可考虑"需要核实什么"的清单，以及基于历史结果的描述性统计。
