## 3. 评估方案

### 3.1 两组对比各算什么

**系统对人工标注**（105 条说明）

| 层面 | 指标 |
|---|---|
| 每个数字 | 是不是金额：一致率 |
| 每个金额 | 计入、不计入、贷记三分类：一致率和各类的召回 |
| 每个计入的金额 | 费用大类：一致率 |
| 每条说明 | 计入金额之和与标注完全相等的比例（主指标） |
| 让错误被看见 | 读错的说明里被送人工的比例；解析通过的说明里读错的比例 |
| 标注为“说不清”的 | 不算对错，只报系统有没有把它送人工 |

每个指标都分开报：

- 三人重叠的 15 条对各包独有的 90 条；
- 按频率抽的一半对从难类别抽的一半（后者不是无偏样本，P-25）；
- 在样本 A 里的 43 条对不在 A 里的 62 条（A 是调优时看过失败的样本）；
- 含购入运输代码对不含；
- 属于 A5 那类 BALANCE DUE 形态的条目单列，不计入对错。

票货层面：全部说明都被标注的票货有 73 票（其中多说明的 8 票），只对这 73 票报汇总总额是否相等，并写明多说明的只有 8 票。如果 H2c 获批，取代逻辑另报。

**系统对 Excel 基线**（开发集全部 813 票货）

- 两种基线：Delta 按不同说明相加；Invoice Dups Removed 减 Shipment Amount。
- 指标：系统默认变化额与每种基线相等的票货数；不相等的按原因归类。
- 归类（事先写定，由代码判定）：文本里的合计被基线重复计入；后一条说明重述了前一条的费用（A3）；BALANCE DUE 是前面金额的 1.03 到 1.07 倍（A5）；基线计入了已付或历史金额；基线漏掉了不带 `$` 的金额；基线只保留了一行；订单副本；未归类。
- 现在已有的参考数（留存读法、未做 A5、仅供量级）：单说明的 722 票里 697 票与基线相等；多说明的 91 票里（1 票有说明没通过检查，不计），直接相加与基线相等的 73 票，按 A3 取代后与基线相等的 26 票。
- 标注覆盖的那部分另报一个三方表：系统对、基线对、都不对、都对。

### 3.2 标注怎么定稿

脚本只做事先写明的机械规则，每一处改动写进修正日志（改前、改后、依据哪条规则）。规则在看任何系统输出之前定下。

| 规则 | 内容 | 谁定 |
|---|---|---|
| R-1 | 标注人编号没填的，按文件名填 P1、P2、P3 | 脚本 |
| R-2 | 非金额的数字，“是否计入”一律置为“非金额”，标注人填了也覆盖（P3 有 2 行） | 脚本 |
| R-3 | 金额没填“是否计入”、计入没选类别的行，标为“结构无效”，所在条目整条不进定稿（P3 共 7 行） | 脚本 |
| R-4 | P3 的“数量和单价标反” | **不由脚本改。** 推荐把这 6 个条目连同指南里的对应例子退回给标注人重标，约 15 分钟；备选是整条剔除 |
| R-5 | BALANCE DUE 加多个金额的条目，三包统一成全部“说不清” | 需要你定。推荐用脚本按一条写明的文字规则统一（“原文含 BALANCE DUE 且另有两个以上 `$` 金额”），因为这是指南原有的要求；备选是请 P1 自己改 |
| R-6 | 三人重叠的 15 条：每个字段取多数；三人各不相同的取“说不清” | 脚本 |
| R-7 | 定稿文件、修正日志、对照表都放在 git 忽略的目录 | 脚本 |

### 3.3 怎么保证标注不被用于调优

1. **顺序**：先完成全部提示词和规则改动（T12-11），冻结版本（提交号、SKILL.md 哈希、规则版本写进 H3 卡），再跑评估。
2. **门槛先写**：主指标的门槛在跑之前写进 H3 卡并提交。
3. **只出汇总**：评估脚本的默认输出只有汇总数和分层数。逐条差异写到 git 忽略的文件，默认不生成，要加参数。
4. **看过即用过**：一旦有人看了逐条差异，这 105 条就不能再作为之后任何改动的证据。之后的改动只能在 B2 和公开 mock 上验证，报告里把标注上的数字标为“改动前”。
5. **读取隔离**：定稿文件的路径只出现在评估脚本里；运行时代码和例子库构建脚本不读它。加一条测试：`src/` 里不出现这个路径。
6. **如实写局限**：标注全部来自开发集；43 条在样本 A 里；4 条属于 Jake 的两个例子；例子库的 5 条不在标注里。
7. 本轮我读了三个标注文件的结构（行数、是否填写、下拉值是否合法），没有拿它们和任何系统输出比对。
