# C1 诊断目录

## 这一块做什么
系统发现的每一类问题都是目录里的一种"诊断"，代码三段：`对象.子类.类型`（对象 = 记录 JSON 里的位置：`REC`、`NUM`、`ITEM`、`CLAIM`、`HIST`、`RUN`）。每种诊断有固定的触发条件、证据格式、处理方式（退回给模型 / 只记录），以及给审核员的说明、给承运商的修改要求和合格标准。打回通知和审核员草稿的文字**只能**取自这里，代码里不写自由文字（02 §4）。严重程度和转人工作用不在目录里，在 `rules.yaml`（C2）。

## 输入和输出
- 文件：`scratch/prototype/diagnostics_catalog.yaml`（原型，未改动）
- 渲染：`scratch/prototype/render_catalog.py` 把目录和规则渲染成 02 §4.3 的表；本交付物的渲染结果在 `results/catalog_rendered.md`

## 一条命令复现
```
sh scratch/deliverables/run.sh C1_catalog_check.py
```
结果写到 `results/summary.md`、`results/catalog_rendered.md`、`results/examples.md`。

## 检验数据
目录本身，加上开发集全量 908 条事件的代码部分运行（看实际触发了哪些诊断、通知文字从哪来）。不是测试集。

## 结果
12 项检查 **全部通过**：
- 61 种诊断：退回 15 种，只记录 46 种（与 02 §4.3 一致）
- 每种都有对象、触发条件、证据、步骤、处理方式；只记录类都有给审核员的说明（退回类只回给模型，不到审核员手里，所以没有）
- 只记录类与 `rules.yaml` 一一对应；退回类不在 `rules.yaml` 里（不生成 flag）
- 有修改要求的都有合格标准，反之亦然
- 原型代码里出现的诊断代码全在目录里；开发集上实际触发的 20 种全在目录里
- 开发集上生成的所有打回通知和草稿，每一句都来自目录

5 种诊断的例子见 `results/examples.md`。

## 局限
- 61 种里有 41 种在只跑代码的开发集运行中没有触发：大多要用到第 3 步的模型输出，只在 17 个合成用例和 02 第 8 节走例里跑过。
- 文字是中文草稿；给承运商的英文措辞、给审核员的界面都还没定。
- 目录的"给审核员的说明"是否有用，要等审核员对 flag 的评价（02 §9.2）。
