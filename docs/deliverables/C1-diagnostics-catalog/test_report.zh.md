## 1. 声称的结论

系统的 61 种诊断各有固定的触发条件、证据、处理方式和说明文字；目录、`rules.yaml` 和原型代码三者一致；开发集上生成的所有打回通知和审核员草稿，每一句都来自目录。

## 2. 为什么是这个证据级别

检验的是目录本身，加上开发集上代码部分的运行；目录和检查脚本出自同一方，没有人工审核。61 种里有 41 种在开发集上没有触发过。属"样本内"。

## 3. 检验方法

`scratch/deliverables/C1_catalog_check.py` 做 12 项一致性检查：条目数和退回 / 只记录的划分；必填字段（只记录类必须有给审核员的说明）；处理方式合法；代码格式 `对象.子类.类型`；只记录类与 `rules.yaml` 一一对应；退回类不在 `rules.yaml` 里；修改要求和合格标准成对出现；原型代码里出现的代码都在目录里；开发集上触发的代码都在目录里；通知和草稿的句子都来自目录。另外运行 `render_catalog.py`，它会断言每种只记录类都有规则配置。

## 4. 检验数据

目录 `scratch/prototype/diagnostics_catalog.yaml`，加开发集全量 908 条事件的代码部分运行（没有第 3 步）。**不是测试集**；没有读原始 Excel。

## 5. 门槛及是否事先设定

**门槛未事先设定。** 期望值"61、15 / 46"来自 02 §4.3，其余各项的期望都是 0（"没有不一致"），是检查时写的。

过程中的一处修正（03 报告第 3 节）：第一版检查要求 61 种全都有"给审核员的说明"，报出 14 条缺失；核对后发现这 14 条都是退回类（只回给模型，02 §4.2、§4.3 本来就写"无"），于是把检查改为只对只记录类要求。这次修改是在看到结果之后做的，这里如实记下。

## 6. 结果

12 / 12 通过（`results/summary.md`）：

- 61 种诊断：退回 15 种、只记录 46 种，与 02 §4.3 一致。
- 缺必填字段 0；处理方式不合法 0；格式不符 0。
- 只记录类缺规则 0；规则里有、目录里没有的 0；退回类误入规则 0。
- 修改要求和合格标准不成对 0。
- 原型代码里有、目录里没有的代码 0；开发集上触发、目录里没有的代码 0。
- 不来自目录的通知或草稿句子 0。
- 按对象分：CLAIM 4、HIST 8、ITEM 17、NUM 15、REC 12、RUN 5。
- 开发集上触发了 20 种，**41 种没有触发**。

## 7. 局限

- 41 种没有触发过的诊断大多要用到第 3 步的模型输出，只在 17 个合成用例和 02 第 8 节走例里跑过。
- 文字是中文草稿；给承运商的英文措辞、给审核员的界面都还没定。
- 说明文字是否有用，要等审核员对 flag 的评价（02 §9.2）。

## 8. 复现命令

在仓库根目录执行：

```
sh scratch/deliverables/run.sh C1_catalog_check.py
```

## 9. 升到深绿的检验方案

- **独立数据或核对人**：(a) 独立样本：为 41 种没触发过的诊断逐种手写合成提交（`Submission`）或合成记录，事先写下每个用例应触发的代码；(b) 人工审核：由写目录以外的组员评审给审核员的说明和给承运商的修改要求。
- **做法**：(a) 把合成用例交给 `check_submission`、`history_diagnostics` 等原型函数运行，看是否触发、生成的文字是否来自目录；(b) 评审逐条标注"清楚 / 不清楚 / 有误"。
- **门槛**：61 / 61 种都能被触发；触发后生成的文字 100% 来自目录；评审没有阻塞性意见 `[建议，待确认]`。门槛要在写合成用例之前写进卡片的完成标准。
- **是否依赖 B04**：部分依赖。合成提交现在就能做；`RUN.*` 类（轮数、提交失败等）只有真实的 agent 运行才会自然触发，合成只能模拟。
