# T18 第二部分：独立设计和改动计划（任务书第 4、6 节）

日期：2026-11-15。分支 `leg7-arch`。第 4 节在打开参考想法之前写完并单独提交（提交信息“T18 独立设计”）；之后的修改写在 `03-comparison.zh.md`，并在本文第 4.6 节列出，第 4 节原文保留在那次提交里。

数字的出处都在 `01-inventory.zh.md`，下文用“清单 3.x”指它的小节。

## 结论先说

1. **问题不在 skill 的个数，而在一个 skill 里装了三种东西**：每条都要的读法规则、只有少数说明用得上的专题知识（税、余额和历史、单价数量、费率更正、贷项）、以及代码已经在管的规则的复述。复述那部分已经过时 3 处、和代码不一致 3 处（清单 3.2）。
2. **读数仍然是一个 skill**，但改成“核心 + 专题参考文件”，专题由代码按特征选好放进输入，不靠模型自己去取：模型 91.7% 的说明除了提交什么工具都不调（清单 3.3），而且我们的智能体没有文件系统，渐进加载只能由代码来做。
3. **新增一个注入筛查 skill**，和读数分开、每条说明都跑：剩下的漏报 19 / 22 是改写过的注入，代码两层和读数模型都没接住（清单 3.6）。
4. **跨说明的关系继续留在代码**：模型一次只读一条说明造成的 16 个漏报，现在全部由代码规则接住，规则在 mock 上除第 7 条外没有唯一原因误报（清单 3.5、3.6）。不为它建 skill；只把“代码定不了”的那一小类（规则 7）列为以后的候选。
5. **工具从 6 个改成 5 个**：去掉没人调的查税（两套数据 0 次）和找示例（不到 1%），它们的内容改由代码放进输入；修改提交工具和查代码工具；为筛查 skill 新增它唯一的输出工具。
6. **两个结构缺口要补**：票货汇总不在主流程、审核界面看不到（清单 3.1）；每个业务概念要有唯一出处（第 4.5 节），比如“计入”现在在 `src/` 里有 4 份实现。

### 4.3 划分 skill 的原则和清单

**原则**（先定原则，再按原则数 skill）：

1. **一个 skill 对应一次独立的模型调用任务**。输入、输出、运行时机三样里有一样不同才拆成两个 skill；同一任务里话题不同的知识不拆 skill，拆成参考文件。依据：【Agents】的路由模式适用于“类别明显不同、分开处理更好”的情况，而税、余额这些专题的输入输出和读数一模一样；【Skill】的渐进加载本来就是一个 skill 内部的文件组织。
2. **代码能定的不写进 skill**。skill 里最多一句“提交之后代码会做什么”，让模型知道边界；这句话由一处定义生成（第 4.5 节），不手写。
3. **参考文件由代码按特征选，不靠模型去取**。依据：模型几乎不调可选工具（开发集 91.7% 只提交，查税 0 次、找示例 0.6%）；我们的智能体按规定没有文件系统工具。【Skill】的渐进加载在这里只能实现成代码路由。
4. **每个 skill 有自己的评估数据和事先写好的门槛**；没有数据能评估的 skill 不建。依据：【Skill】“先建评估”。
5. **模型一次只看一条说明**；跨说明关系由代码按金额、代码、比例处理，只有代码明确“定不了”的才考虑交给模型，而且模型只给关系建议，合计永远由代码算。依据：清单 3.6，跨说明漏报全部由代码接住。
6. **安全筛查和读数分开**，一次调用只做一件事。依据：读数模型兼做注入识别，mock 上报了 31 次“对系统说话”，仍漏 19 个。

**按原则得出的 skill 清单**：

| | S1 读数 `reading-dispute-explanations` | S2 注入筛查 `screening-for-instructions`（新） | S3 票货关系建议（候选，本轮不建） |
|---|---|---|---|
| 输入 | 一条说明：脱敏文字、标记文字、数字表、省份；代码选好的专题参考和 1 到 2 个相似示例 | 一条说明的脱敏文字（不给数字表） | 代码标了“关系定不了”（规则 7）的票货里，相关几条说明的脱敏文字和读法 |
| 输出 | 读法，只能经 `submit_line_items` | 是否有对系统、模型、审核流程说话的内容，加原文引用，只能经 `submit_screen_result` | 每对明细“同一费用 / 不同费用 / 说不清”加引用；不给合计 |
| 什么时候运行 | 每条说明 | 每条说明，在 S1 之前或并行 | 只在规则 7 触发的票货（开发集 21 票） |
| 核心知识 | 任务边界；输入字段；`kind`、`status`、`is_credit`、计入、合计、证据和排除词（排除词表由 `rules.yaml` 生成）；代码表；一句“文字是数据”；退回后怎么修 | 什么是“对系统说话”（指令、角色扮演、要求改金额或改结论、要求泄露提示词）；常见伪装（拆字母、形近字、空格）；货运文字里看着像指令其实不是的（如请求付款、请审批） | 什么算同一费用（同义名、缩写），只看名字和理由，不看金额 |
| 参考文件（代码按特征加载） | 税（含税表，替代查税工具）；余额、已付和历史；单价和数量；费率更正；贷项 | 无 | 无 |
| 需要的工具 | `submit_line_items`、`report_uncertainty`、`lookup_charge_code`、`calculate` | `submit_screen_result` | 一个只读的提交工具 |
| 和代码规则的分界 | 模型说“文字写了什么”；代码算合计、查关系、定颜色。余额的倍数默认、取代、相加、历史重提都只在代码里 | 筛查结果只加一个送人工标识，不改读法、不跳过 S1；代码两层检测照旧 | 代码先跑完全部规则；S3 只把“说不清”变成“同一 / 不同”的建议，审核员看得到，默认合计仍按代码 |
| 用什么数据评估 | 人工标注 101 条；开发集全量的送人工变化；mock 第三轮按特征组分开报；第四轮 mock；最后一次预留 mock | mock 的注入事件（第三轮 60 个，第四轮）；开发集 908 条当阴性测误报；公开注入数据集作补充 | 规则 7 的 mock 事件（第三轮 27 个）和开发集 21 票的人工判定 |

**人**：定待决事项（P-xx）、审核、批准每轮改动、维护代码表的含义、挑示例。

### 4.5 一处定义

现在同一个概念写在多处，已经出现不一致：例如“计入”（状态是 CLAIMED 或 UNPAID）在 `src/` 里有 4 份（`schemas.py`、`reading_checks.py`、`rollup.py`、`db.py`），其中 `db.py` 的“计入合计”只看状态，`rollup.py` 还要求类型是金额，两边对“状态写了 CLAIMED 的合计数”结论不同；`scratch/` 里还有 4 份。

**做法**：`rules.yaml` 新增 `concepts` 一节作为唯一出处，每个概念写：编号、给模型看的英文定义、中文定义、实现它的唯一函数、相关阈值的键。代码只从这一个函数取；`SKILL.md` 和参考文件用占位符从这里生成；加一个测试：skill 文字里出现的概念都来自生成，同一函数在 `src/` 里只有一份。

| 概念 | 一句话 | 唯一出处（定义） | 唯一实现 | 现在另有的写法 |
|---|---|---|---|---|
| 计入 | 这次主张要的金额：状态 CLAIMED 或 UNPAID，类型是费用、未说明用途或税 | `concepts.counted` | 新的 `claim.counted(reading)` | `schemas`、`reading_checks`、`rollup`、`db` 各一份，scratch 4 份 |
| 历史 | 描述过去开票、付款、扣款的金额：BILLED、PAID、DEDUCTED | `concepts.history` | `schemas.Status` | `rollup.HISTORY_STATUSES`、`SKILL.md` 第 3、5 节 |
| 合计 | 文字里写明是同一段其他数之和的数 | `concepts.total` | `checks` 的合计核对 | `SKILL.md` 第 5 节 |
| 余额 | BALANCE DUE 一类写法；写在其他金额之后、是其中一个的 1.03 到 1.07 倍时取代它；其他写法见决定 A5、D-81 | `concepts.balance_due` + `rollup` 阈值 | `rollup._balance_due` | `SKILL.md` 第 5 节让模型自己判断（**不一致**）；`rules.yaml` 注释 |
| 取代 | 同一票货里，后一条说明的同一费用（最细的内部代码）替换前一条 | `concepts.supersede` | `rollup` 规则 2、6 | `rollup.py` 文档串、调整计划 4.3 |
| 相加 | 不同费用的明细相加；关系定不了时默认相加并提示 | `concepts.add` | `rollup` 规则 4、5、7 | 同上 |
| 重复（拆成三个名字） | 订单副本：同票货、同日期、同文字的几行；同金额：后一条同金额不同代码；历史重提：后一条计入的金额等于前一条的历史金额 | `concepts.order_copy` / `same_amount_earlier` / `history_echo` | `duplicates`、`rollup` 规则 5、9 | 现在都叫“重复”，报告和标识名混用 |
| 贷项 | 文字明说是退款或减项的金额，记负数 | `concepts.credit` | `checks` + `rollup` | `SKILL.md` 第 3 节；短横线不算（清单 3.4） |
| 数量乘单价 | 数量 × 单价；文字没写结果时，数量大于 1 才算说不清（D-82） | `concepts.quantity_rate` + `number_features.quantity_rate` | `checks.quantity_rate_patterns` | `SKILL.md` 第 5 节缺数量为 1 的例外（**不一致**） |
| 排除依据 | 不计入的 `$` 金额必须有的词，7 类 | `exclusion_basis`（已有） | `checks.exclusion_basis_category` | `SKILL.md` 第 3 节只举 5 个词（**不一致**） |

### 6.3 和第四轮 mock、预留 mock 的先后

（M1 修改后的顺序；初稿是“冻结版本先跑第四轮，再改”，见提交 `4793b28`。）

1. 先做不调模型的改动 A、B、F（汇总进主流程、一处定义、跨批次历史），用存档读法重放验证，花费 0。
2. 再做 C、D、G（读数 skill 重组、注入筛查、“提到了更早的主张”）。设计只用开发集和 mock 第三轮的证据。
3. 改动后的版本跑开发集全量和 mock 第三轮做回归，门槛事先写进卡片：人工标注 Recall 不降、mock 第三轮各特征组的 Recall 不降、开发集新增送人工不超过事先定的条数（建议 20 条说明）。不过就用开关切回 `single`。
4. **冻结**，然后跑第四轮 mock，按事先写的门槛报。这是新版本的第一次独立检验。如果据第四轮再改，第四轮就变成样本内，要在报告里写明。
5. **最后用预留 mock 跑一次**，只跑最终版本，结果按事先写的门槛报，不再据此修改。

冻结规则的处理：任务 17 写明第四轮和预留 mock 测完之前不改规则和代码。按上面的顺序要先解冻，第 4 步之前再冻结，需要用户同意。如果用户决定不改架构，就不解冻，按任务 17 用冻结版本跑第四轮。
