# 项目总结（2026-11-16，MVP v1）

CMU Intro to AI 客户项目（第 16 组，客户 PPG）。对应标签 `mvp-v1.2`（分支 `mvp-v1`）。英文版：
[`2026-11-16_project_summary.md`](2026-11-16_project_summary.md)。下面每个数字都标明证据级别：**样本内**（开发时看过的数据）、
**独立检验**（开发时没用过的数据）、**人工标注**（和人写的答案比）。

## 1. 产品是什么、给谁用

承运商要 PPG 多付运费时，会用一段文字解释调整（"LIFTGATE $50 + GST $2.50"、"BALANCE DUE IS ..."），现在由审核员逐条人工读。
系统把每段说明变成结构化明细（费用、金额、税单列），对照原文本身检查，把同一票货的各条说明汇总成客户格式的表（原始运费、各项费用、
新总额、变化），并打标识告诉审核员该看哪里。建议只有三种：解析通过检查、建议人工审核、建议退回承运商。系统从不决定一笔费用该不该付。

使用者：PPG 的运费审核员（票货表和审核页面）；读结构化输出的下游系统（读法接口说明和票货接口说明）。

## 2. 分工（代码、工具、skill、人各管什么）

"代码"是确定性的；"skill"是由 skill 文件指导的一次模型调用；"工具"是模型可以调用的函数。

| 工作 | 谁做 | 在哪里 |
|---|---|---|
| 读入行、把订单副本合并成说明 | 代码 | `records.py`、`duplicates.py` |
| 调模型前遮掉人名和邮箱 | 代码 | `textprep.redact` |
| 发现对系统说话的文字（注入） | 代码（两层）+ skill `screening-for-instructions` | `textprep`、`screen.py` |
| 数字表：每个数一个编号 | 代码 | `numbers.py` |
| 说清每个编号的金额是什么（是不是钱、这次要还是历史、费用、理由、文字写明的应付数） | skill `freight-dispute-line-items` | `SKILL.md` + 代码挑选的专题参考 |
| 费用名到代码；精确算术 | 工具 `lookup_charge_code`、`calculate` | `tools.py` |
| 检查读法（编号存在、引用在原文里、算术成立） | 工具 `submit_line_items` 里的代码 | `checks.py` |
| 票货汇总、BALANCE DUE 规则、gap、另一读法总额 | 代码 | `rollup.py`、`pipeline.finish_batch` |
| 客户费用名、客户格式的表 | 代码 | `charge_map.py`、`shipment_table.py` |
| 标识到建议 | 代码，门槛在 `config/rules.yaml` | `disposition.py` |
| 审核决定 | 人，在本地页面上 | `review_ui.py` |
| 改进规则和 skill | 人定；Claude Code 提方案并验证 | `scratch/eval/` |

模型只描述文字写了什么、只引用数字编号：不能写入原文里没有的数字，给金额的正负号也必须有原文依据（贷记词、括号或紧贴的负号），由代码核对；它也看不到任何预期总额。所有总额和颜色都由代码算。

## 3. 关键决定（每条一句；全部见 `docs/autorun/decision_log.zh.md`）

1. 每条记录都过模型、再交给人；模型之前不打回任何记录（决定 2.1）。
2. 任何地方都没有批准、拒付或付款输出；审核按钮记录的是"认可这份读法"（D-99）。
3. 客户的 Delta、Invoice Amount、Invoice Dups Removed 是表格估算：只作评估基线，从不给模型看（客户 11-13 答复）。
4. 费用属于票货：同一辆车上的订单副本是一条说明，只读一次（客户答复）。
5. 后一条说明的同一费用（最细的内部代码）取代前一条；不同费用相加（A3）。
6. BALANCE DUE 金额是前面某金额的 1.03 到 1.07 倍时取代它；不论写在哪里，对不上已定关系的送人工（A5、D-81、D-95）。
7. 税单列一行，跟着它所在的说明走。
8. gap（文字写明的应付数 − 明细合计）单独一栏，只提示（D-96）。
9. 人名脱敏用按事先规则选出的白名单方法（任务 10）。
10. 每个业务概念只在 `rules.yaml` 的 `concepts` 里定义一次，skill 文字从这里生成（任务 19）。
11. 读数 skill = 核心 + 由代码挑选的专题参考（`routed` 布局，任务 19）。
12. 另设注入筛查 skill：只加标识，不改读法（D-85）。
13. 评估门槛在跑之前写进状态卡（状态板规则）。
14. 代码里没有针对某个承运商的规则；承运商写法只出现在示例数据里（项目规则）。

## 6. 已知局限

- 独立证据很少：只有第四轮 mock 新增的 122 个合成事件（6 个阳性）开发时没看过。
- 开发集约 59% 的行来自一个承运商、一种费用，总体数字主要反映它。
- 单个金额读错，只有模型自报疑问或代码检查碰上才会发现；按决定不和外部总额比。
- 跨说明的关系只靠代码、金额和倍数判断，还没有取文字里"更正、替换"这类词；跨批次历史没接上（显示"未提供"）。
- gap 只给单说明票货。
- 脱敏对合成人名的漏遮率约 10.9%（任务 10 测量）。
