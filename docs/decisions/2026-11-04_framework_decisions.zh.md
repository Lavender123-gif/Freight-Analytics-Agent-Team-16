## 1. 定位与范围

1. `[定]` 产品是一个"齿轮"：把承运商的自由文字标准化成干净的结构化数据，给审核员和下游系统使用。
2. `[定]` 判断一笔费用该不该付，不在范围内。给审核员提供帮助他做决定的**事实**（例如起讫地距离、同一票货下有几笔相同的争议），在范围内。
3. `[定]` 只按 Excel 开发，不设计任何 API 接口。读取 Excel 的代码集中在一处。
4. `[定]` 验证立场：不存在真值。PPG 自己的处理、审核员的判断，也只是各自脑子里的规则。我们的目标是把规则写明白，确保 agent 稳定地识别出规则内的异常，并在 mock 数据上验证这一点。
   - 例外：模型"读得对不对"（例如文字里 318.18 是不是滞留费的金额）有真值，任何人看原文都能确认。这部分要用真实文字加人工核对来测，mock 代替不了。
5. `[定]` 查重和标识的规则放在 `rules.yaml`（代码读取），不放在给模型读的 `SKILL.md`。PPG 以后可以增改规则。从规则文件自动生成一份大白话的规则说明给 PPG 看。
6. `[定]` 不追求第一轮就让审核员满意，靠反馈调试。产品目标是标识不要太多。
7. `[定]` 定期从**没有标识**的记录里抽一小部分给人看，用来发现我们漏写的规则（标多了会有人抱怨，标少了没人会说）。
8. `[定]` 审核界面算正式交付物。动手之前先看开源的人工审核和标注工具（例如 Label Studio、Argilla）能否满足，再决定自建哪些部分。

## 2. 流程

1. `[定]` 所有记录都进模型。删除模型之前的打回分支；"空文本""只有数字"改为普通诊断。
2. `[定]` 系统不做任何动作。删除自动通知承运商的开关和相关事件类型。所有记录都交给审核员；"退回"只生成一份草稿供审核员使用。
3. `[定]` 推荐三类，以颜色呈现：正常、有标识、建议退回。
   - 颜色由规则算出，不用模型自评的把握程度。模型主动报告的疑问，是规则的输入之一。
   - 判断顺序：先看有没有需要人看的问题，再看有没有可以退回的问题，都没有才是正常。
   - 全部检查都通过的记录，同样交给审核员，只是不加标识。

## 3. 模型怎么读，读完怎么查

1. `[定]` **盲解析**：模型的输入里不含 Delta。现在 `SKILL.md` 第 2 节输入里的 `delta`、`delta_sign` 要去掉，试算工具（reconcile）也要去掉。
2. `[定]` **不一致的处理**：模型给出每个数字的解读和整笔主张的金额，代码拿它和 Delta 比。
   - 不一致时告诉模型"不一致，不一定是你错了，也可能是 Delta 错了"，不透露 Delta 的值。
   - 模型可以坚持，也可以修改；修改时必须说明它认为自己错在哪里。
   - 每一次尝试都保留。第一次的读法在审核界面上可见。
   - 不一致的情况呈现给审核员判断，系统不裁决。
   - `[待讨论]` 重试次数，倾向 1 到 2 次。
3. `[定]` **算式**：模型的输出必须写明它看到的算式关系（哪几个数构成一个算式，各自是数量、单价还是结果），代码每次都验算，不管模型自己算没算过。
   - 原文数字旁边出现 `@`、`X`、`PER`、`DAYS` 这类迹象，而模型没有写任何算式关系，打一个提示。
   - 可以另外给模型一个计算器在思考时用，但不能替代提交后的强制验算。
   - `[待模型验证]` 模型在不被提示时会不会自己发现算式错误。
4. `[定]` "合计被算两次"不再作为门槛。不一致时，代码可以给审核员加一句解释（例如"Delta 恰好等于各项加合计"），可选。
5. `[定]` **防凑数**：带 `$` 却没有算进本次主张的金额，必须有原文依据（例如原文确实写了 `PAID`）。代码自动比较前后两次尝试，把改了状态的数字列给审核员。独立的第二次解析放进实验。
6. `[定]` **费用代码**：模型用代码表和别名表识别。之后代码检查模型给出的依据片段确实是一个费用名称、在不在该代码的别名里；不在就打"不常见的对应"提示，不算错。语义对错靠人工标注评估。
7. `[定]` **"其他"**：代码表里找不到就打标识。原文写进说明，同时单独存一个原文费用名称字段（有没有金额都能存），以后用来扩充代码表。
8. `[定]` **认不出的数字区域**：去掉"这里没有数字"这个选项，模型必须逐位写出并判断。
9. `[定]` **没通过检查的提交**：审核界面照样显示，并加标识；数据里用状态字段明确区分，下游只能读通过的。
10. `[待讨论]` 模型的哪些判断要留痕：随 schema 一起定（任务 06 给出基线方案）。

## 4. 数据与历史

1. `[定]` **历史**：原始事实以 Excel（Oracle 导出）为准，我们不复制、不维护。我们**存自己的解析结果**，用于跨批次比较。这一条修改了 Codex 审阅任务书第 3 节第 5 条"系统本身不维护跨批次的数据库"。理由：查重要比的是解析后的结果，Oracle 里没有；每次重新解析历史既费钱，结果也可能不稳定。
2. `[定]` 默认不给模型看历史，由代码比对，审核员在界面上看。给不给模型看，留作对照实验。
3. `[定]` **加拿大在范围内**。开发集 953 行里 790 行是加拿大到加拿大。`US/CAN` 这一栏不可信（例如卡尔加里到卡尔加里写的是 `US`）。国家从起讫省州推出；币种放在记录一级，按国家推算，标为"推算"。`[待 Jake]` 币种的真实来源。
4. `[定]` **税**：税的规则跟 Jake 确认之前，税的问题一律送人工，不判承运商算错。`[待 Jake]` 适用省份规则。
5. `[定]` **字段原则**：每个字段标明读者（审核员、下游系统、我们自己的审计和评估）和来源（Excel 原样、代码推算、模型判断、审核员决定）。不属于任何读者的字段删掉。JSON 从数据库结构导出，先定表再定 JSON。
6. **用户在原始数据里观察到的一例**（需要在开发集上核实是否普遍）：
   - 同一票货、同一个承运商发票号下，两笔不同的费用（滞留费、搬卸费）各自在 8 个不同的 PK 下出现。每组的文字、Delta、时间（精确到分钟）完全相同。8 个 PK 里有 7 个的编号日期，比争议时间晚将近两个月。
   - `Invoice Amount` = `Shipment Amount` + 该行自己的 Delta，不是发票合计。
   - `Invoice Dups Removed` 只在这张发票（或这票货）的第一行保留金额，其余行为 0，导致其他费用从合计里消失。**这一列不可用**。
   - 这是导出复制，还是 8 次真实的 change order，没有定论。`[待 Jake]`

## 5. 重复

1. `[定]` 只打标识，不判断是否正常，由审核员决定。
2. `[定]` 多层面查重，至少包括：行层面（除 PK 外全部相同）、发票内（同一张发票里同一种费用出现两次）、票货内跨发票（同一票货的不同发票里出现同样的费用和金额）。每一层有自己的检查。下层先处理，再往上比，避免复制品在上层被重复计数。
3. `[定]` 每份复制品都是独立记录：
   - 第一份不标红，但带一条提示"后面还有 N 笔相同"。
   - 后面每一份标红，并指向第一份，各自独立审核、独立清除。
   - 支持批量清除（一次点完，但每笔各自记录清除动作和理由）。
   - 跨批次时，"第一份"指之前批次里已经见过的那份。
   - `[待讨论]` 批次内"第一份"按 PK 还是按 Excel 行号确定。
4. `[定]` 下游汇总在审核员清理之后计算，所以存成几笔不影响汇总。
5. `[定]` 重复的成因和特征从数据中总结（**不看** `Invoice Dups Removed` 这一列），据此造 mock，规则在 mock 上验证。
6. `[待讨论]` 我们自己做统计和评估时，复制品怎么计数。倾向：在 mock 上把逻辑做对即可，真实数据上的笔数不作为任何结论的依据。

## 6. 审核界面

1. `[定]` 一批跑完，列出 N 张发票。每张带状态颜色和三角图标，图标按严重程度分开计数（例如"2 个建议退回、3 个需留意"）。列表可以按"有没有提醒"筛选和排序。
2. `[定]` 点开一张发票，先看到总览：基本信息（票货、承运商、发票号、起讫地和距离、运费）、模型读数合计与 Delta 合计的对账、争议列表、按严重程度排序的标识、这票货在之前批次里的上下文。
3. `[定]` 每笔争议带模型的说明，不点开也能从颜色看出状态。有提醒的争议默认展开，没提醒的折叠。
4. `[定]` 操作按钮放在争议一层：批准、退回承运商（自动附草稿，可修改）、清除标识（必须选或填理由）、暂缓。发票一层只放批量操作（例如"批准所有无标识的争议"）。
5. `[定]` 按钮不改动 OTM。它们的作用是记录审核员的决定（以后的标准答案）和生成可以直接用的东西。审核员的决定不能不加筛选地当作标准答案。`[待 Jake]` OTM 里审核员有哪几种操作。
6. `[定]` 距离：优先用 OTM 的计划里程 `[待 Jake]`；没有的话，用城市中心点之间的直线距离在本地计算，不把地址发给外部服务。先看数据，确认它对哪几类费用有用。
